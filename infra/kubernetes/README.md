# M0-13 Kubernetes platform templates

Build the offline environments with `kustomize build infra/kubernetes/overlays/testing` and `kustomize build infra/kubernetes/overlays/staging`. Both use Kustomize v5.7.1. The .invalid hostnames and application image repositories are deliberate offline fixtures. Application digests come from local OCI descriptors. Authorized activation requires the selected bundle and independently approved template parameters.

The infrastructure operator owns namespace policies, RBAC, reference PodTemplates and admission bindings. Install platform objects and verify the API rejects negative fixtures before admitting workloads. The poller can modify named application Deployments and submit a bounded migration Job. It cannot modify the reference PodTemplates. Subject the trusted references and workload manifests to the same config and digest substitutions. The initial application replicas are zero and application admission parameters are closed. Backing stores can start for recovery. Kubernetes admission validates registered templates. The host launch supervisor checks each actual process start against its current permit.

Worker and the trusted executor share a Judge Pod, a bounded ephemeral testcase cache and a loopback gRPC endpoint. Only the executor container has elevated privileges and its cache mount is read-only. Only the Worker port is a Service. Recreating the Pod invalidates this derived cache. Guard binaries and per-workload permit directories are installed by the platform. The hosts and privileged daemon are trusted. Keep the ingress session authorizer closed until mTLS, current tester lease and release readiness succeed.

For offline verification run `tests/check-render.py KUBERNETES_OPENAPI TRAEFIK_CRDS TESTING_RENDER STAGING_RENDER` with Python, PyYAML and jsonschema. Use Kubernetes v1.35.10 api/openapi-spec/swagger.json (SHA-256 `483500149ee52ce5753d75f5639101d985bb4f5e902cc05b1ba7627465d62446`) and Traefik v3.7.15 docs/content/reference/dynamic-configuration/kubernetes-crd-definition-v1.yml (`ecbe44ea9b011cda1b562716175b882d59cf6561fe6d3e5832df7ee072687d17`). Run `bash tests/check-admission.sh TESTING_RENDER` with kube-apiserver and kubectl v1.35.10, etcd v3.6.5, openssl and Python on PATH. The script starts a temporary loopback API with its own CA and store. It exercises admission and authorization without scheduling Pods. S3 must verify actual sandbox execution, credentials, host networking and resource limits.

The Judge uses the bundled runc implementation with the containerd v3 drop-in from cloud-init. Its OCI base comes from the pinned `k3s ctr oci spec` with a private cgroup namespace added. The Judge Pod also sets `hostUsers: false`. The daemon can delegate CPU, memory and process controllers within its own cgroup. On an authorized test Judge with a current running Pod, run `python3 tests/observe-executor.py astracode-judge "$POD_UID"` on the host to inspect the actual namespaces, device list and cgroup delegation. The owner-approved host trust model still applies. Verify enforcement for real official and interactive jobs during S3.
