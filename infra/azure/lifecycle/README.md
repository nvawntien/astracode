# Managed activation

These modules implement the App participant of task 1.4. The protected controller endpoint and publication paths belong to tasks 1.5 and 1.6. `test_rollout.py` integrates the normal App rollout, issuer and durable-record transitions using node, database and smoke fixtures. Separate real PostgreSQL, Kafka and disposable K3s checks exercise those adapters. These checks do not attest a full Azure deployment.

The poller runs as `astra-poller` with the named workload rollout kubeconfig. The activation service runs as `astra-activation` with the permit issuer key, the named PodTemplate/configuration role and the database fence login. The loader owns its separate kubeconfig and runtime secret delivery. Host sockets verify the peer's Unix UID. Node observers use their per-node Kubernetes role. Judge receives the issuer public key and its scoped node observer credential.

Build `pkg/cmd/astra-launch-guard` and `pkg/cmd/judge-rollout-probe` with the repository Go toolchain for Linux amd64. Run `bash infra/azure/lifecycle/package-app.sh OUTPUT.tar` to package the App Python and SQL files. The protected provisioning entry point `install-platform.sh ARTIFACT_DIRECTORY GUARD_SHA256 APP_TAR_SHA256 PROBE_SHA256` verifies the binaries and package against operator-approved hashes. Judge requires only the first two arguments. Install credentials and protected JSON settings with their owning service's read permission before starting the host units.

App settings in `poller.json` bind the controller HTTPS endpoint and audience, poller client ID, private Kafka and Problem IPs, Problem probe metadata, smoke HTTPS origin, client certificate paths and pre-authorized application fixtures. `activation.json` binds the same controller endpoint and the platform-approved executor digest. Infrastructure provisioning supplies these values. They carry environment-specific input and stay outside the package. `secret-loader.json` binds the loader client ID and exact Key Vault hostname.

Run `bootstrap-host.py --system-id EXPECTED_ID --credential-directory PRIVATE_DIRECTORY` from the installed package under the protected database bootstrap identity. Its libpq service file defines `astra_bootstrap` and one `astra_bootstrap_OWNER` for each database. The private directory contains the generated `fencer`, `drain`, `auth`, `problem` and `submission` passwords. The activation service receives only the resulting fence login through `astra_fence_OWNER` libpq entries. Install `astra_drain_submission` in the poller-only libpq service file `/etc/astracode/drain-pg-service.conf`. This login can only read aggregate retained-work counts. Workload credentials are delivered to the designated Secrets. The runtime loader validates distinct service credentials and derives the Envoy JWK from Auth's signing secret.

The rollout closes ingress, captures prior Submission identity, revokes process permits, confirms termination and stops old controllers before changing their admission references. Migration sessions hold the per-owner lock through preflight, credential issuance and post-check. A retained attempt requires explicit recovery with matching observed histories and confirmed old Job termination. Only after all owners are reconciled does the loader conditionally erase the old attempt's Secret. A partially advanced schema stays closed for a separately approved forward deployment.

During protected infrastructure bootstrap, deliver backing-service credentials before waiting for PostgreSQL protocol readiness and running `bootstrap-host.py`. Provision distinct MinIO users and bucket policies for Auth avatars and Problem testcases from the same protected credential inventory; ordinary service credentials must not be MinIO root credentials. The reviewed Kafka initialization Job is initially suspended. The infrastructure operator unsuspends `job/kafka-init` in `astracode-app` and verifies successful completion before enabling the poller. Its existing script waits for the broker protocol and idempotently creates jobs, results and DLT topics. The routine release identity has no Kafka initialization or backing-service rollout authority. The single-broker template explicitly sets internal topic replication and minimum ISR to 1.

Each process permit binds the environment, operation, session, both node epochs, Pod UID, PID namespace, image/configuration digests and expiry. The node checks the requested OCI reference against CRI image descriptors. It hashes public ConfigMap mounts before issuing evidence. The guard terminates its child when authorization expires or is revoked. A restarted container with a different PID namespace cannot use the previous process permit. The candidate relies on the Judge trust boundary in Proposed ADR-0012 and the staging control plane in Proposed ADR-0013. [Proposed ADR-0012](../../../docs/architecture/adr/0012-judge-executor-trust-boundary.md) · [Proposed ADR-0013](../../../docs/architecture/adr/0013-staging-lifecycle-control-plane-and-identity.md)

Run the Python unit fixtures directly. `test_smoke.py` uses loopback HTTPS with synthetic accounts and mTLS. `test-redis-acl.py` and `infra/postgres/managed/tests/check-fence.py` use disposable containers with networking disabled. The PostgreSQL fixture requires the locally built `astra-m013-migrator:offline` image. `test-kafka-probe.py PATH_TO_BUILT_PROBE` creates an internal Docker network and temporary broker, checking first initialization, active membership and retained work. `test_native_job.py` runs only inside the disposable `m013-fixture` K3s VM; it checks suspended Job recreation and stale UID deletion refusal. The Kubernetes guard and hard-stop fixtures require the dedicated disposable VM described in their source. Real Azure isolation, workload limits, protected approvals and recovery remain mandatory in the S3 rehearsal.

See [controller operations](controller/README.md) for approval, expiry, tester routing and emergency cleanup.
