# Exact-revision release delivery

Phase A defines these paths and exercises them offline. Keep `M013_PUBLICATION_ENABLED` and `M013_DELIVERY_ENABLED` disabled until the separately authorized transition and live verification. The manual startup and protected automated delivery model is recorded in Accepted ADR-0013. [Accepted ADR-0013](../../docs/architecture/adr/0013-staging-lifecycle-control-plane-and-identity.md)

`release-images.yml` accepts protected `develop` pushes only. It calls the reviewed reusable publisher on protected `main`. Each exact source SHA runs the existing Go, database, frontend, gateway, Compose, deployment-script, benchmark and six image checks, plus strict OpenSpec. Existing check names remain intact. CI records its explicit checkout SHA, run, attempt and linked outcome. Publication has a separate job with registry and S4 receipt permissions. PR checks have neither permission.

The publisher builds six application images and the managed migrator from that revision, resolves dependency pins, renders both environments, extracts the migration image's SQL and prefix fingerprints, and checks SQL against the owning source directories. The OCI bundle contains all 13 image pins, environment configuration bytes and hashes, source/configuration revision and CI evidence. It uses the existing Dockerfiles and Kustomize v5.7.1. Azure CLI is pinned to 2.76.0, Buildx to v0.29.1 and BuildKit to the v0.25.1 OCI digest in the workflow; third-party Actions use commit revisions. Publication does not update the infrastructure operator's approved executor digest or workload templates. A newly built executor requires the existing platform approval before activation.

Canonical receipts are created in S4 `canonical-releases`, keyed by the full merge SHA, only after OCI publication and verification. `If-None-Match: *` prevents replacement; the locked container retention policy and scoped role are provisioned separately. A retry verifies and adopts the first complete receipt. A different bundle for the same SHA reports a conflict. An interrupted image/bundle upload leaves no selectable receipt. Concurrency groups include the source SHA, so another passing merge cannot cancel its checks or publication. Reconciliation on `main` accepts no SHA input: it enumerates missing, PR-backed merges from an owner-reviewed inclusive `M013_FIRST_MERGE` to protected `origin/develop`. The lower bound must include the merge introducing M0-13. A batch processes up to 64 missing receipts; subsequent runs continue the remaining history.

Pre-merge S3 read-only checks and rehearsal packaging can run before workflow registration. The protected automatic S3 deployment requires the separately authorized minimal default-branch registration. An authorized maintainer applies `m013-rehearsal` to the candidate PR. `rehearsal-checks.yml` runs read-only CI and strict validation against the explicit head SHA. After separate Phase B authorization, the protected operator checks out that exact reviewed SHA, uses a GHCR-only publication credential and runs:

```sh
python3 scripts/release/rehearsal.py --source /protected/candidate \
  --reviewed-source FULL_REVIEWED_SHA --run PASSING_REHEARSAL_RUN_ID \
  --output /protected/evidence/rehearsal.json
```

The operator sets `GITHUB_REPOSITORY=nvawntien/astracode`, `GITHUB_ACTOR` and a protected `GH_TOKEN`, authenticates Docker to GHCR without printing the credential, and installs the pinned Kustomize/PyYAML tooling. The command independently reads the run and every required job, checks their source and results, then uses the same build/packaging function as canonical publication. It writes only to the rehearsal registry namespace and never accesses S4. The resulting `rehearsal` bundle is ineligible for S2 and promotion. `rehearsal-release.yml` offers the same packaging path after default-branch registration, behind the owner-reviewed `testing-rehearsal` environment.

`staging-deploy.yml` freezes slot, action, full source revision, immutable release digest and compatible fallback before native Environment review. The S2 and S3 environments use separate scoped federated principals. Execution serializes per slot, requires a new run with fresh approval for a retry and invokes only the fixed App rollout command through Azure Action Run Command. The App validates actual authorization and immutable receipts, then performs migration, rollout and smoke. Publish sanitized per-run evidence with the observed image, config and schema digests. The workflow has no startup, S4 state or publishing role.

`promotion-eligibility.yml` resolves a semantic tag through the reviewed `promotions.json` on protected main and independently checks the exact successful S2 delivery run, its native review history, its artifact and the canonical S4 receipt. The eligibility reader has no package write, VM power or deployment role. The initial tag mapping is empty. Add reviewed mappings only when a canonical release has eligible S2 evidence. This workflow does not build or deploy production.

Run `python3 -B scripts/release/test_policy.py` and `actionlint` offline. `test_package.py MIGRATION_DIRECTORY` consumes `/migrations` extracted from the local managed migrator image, renders both overlays and exercises the App catalog/unpacker. Its CI proof is deliberately synthetic and is never published. Live registry permissions, receipt immutability and reachability, workflow registration, native approvals and federation remain mandatory Phase B checks.

## Separately reviewed default-branch transition

Prepare a small maintenance PR against `main` after owner authorization; do not merge the milestone branch or create a release tag to register workflows. Copy only the reviewed workflow definitions below, their `scripts/release/` helpers, `infra/azure/lifecycle/configuration.py` (public configuration hashing), and the corresponding workflow assertions in `scripts/deploy-release-transition_test.py`. Preserve the existing CI jobs and names when applying the exact-SHA input, evidence and concurrency additions. Review this file list against the actual `main` tree; include `staging-deploy.yml` and `scripts/release/delivery.py`.

- Register `release-candidate.yml`, `reconcile-releases.yml`, `rehearsal-release.yml` and `promotion-eligibility.yml`, and `staging-deploy.yml`. Make `openspec.yml` reusable for an exact SHA.
- Replace maintained `release-images.yml` triggers with protected `develop` push only; retire arbitrary-SHA/manual and tag publishers. The reusable trusted publication path is `nvawntien/astracode/.github/workflows/release-candidate.yml@refs/heads/main`.
- Retire `deploy-production.yml` as in this change. Independently disable that workflow at repository level so historical refs cannot run it; revoke or leave inactive every legacy SSH/production credential. Keep Compose deployment scripts as reference.
- Restrict canonical publication federation to the registered trusted workflow and protected environment/ref context. Remove historical publisher identities and catalog access. Neither publisher nor eligibility reader receives staging power or deployment roles. Verify the actual GitHub OIDC subject customization and Entra federation before enabling publication.
- Set protected branch/ruleset checks, review requirements and the inclusive reconciliation lower bound. Configure the separately scoped S4 account/tenant/publisher variables, GHCR access, `canonical-publication`, `testing-rehearsal` and `promotion-eligibility` environments, and separate `s2-delivery` and `s3-delivery` environments. Validate workflow registration and wrong-ref/legacy/rehearsal rejection on the real refs before turning on either enable flag.

Repository workflow retirement alone cannot disable a historical workflow run or revoke cloud credentials. That external transition requires separate owner authorization. Register only the required S3 workflow before rehearsal. Repeat the production-legacy and canonical S2 checks at Task 3.1. No such changes have been made during Phase A.

For delivery, use native required reviewers with no self-review or administrative bypass. Restrict protected environments to main. The expected Azure federation subject combines the immutable `repository_id`, exact `environment`, `ref` and `workflow_ref`. Confirm the emitted subject and preserve existing publisher federation before changing any repository-level customization. Populate the slot-specific target subscription, tenant and protected App-only delivery client ID using environment values. Verify both allowed and wrong-ref, wrong-workflow and wrong-target cases before live activation.
