## Goals / Non-Goals

**Goals:** Make every one of the 22 behavioral requirements traceable to executable production code, distinguish supporting tests from code inspection, and preserve current compatibility and limitations.

**Non-Goals:** Runtime implementation, remediation of Findings, deployment, migration, archive, main-spec edits, or specifying `judging` or `realtime-updates`. No schema, event, authentication, gateway, or sandbox change is proposed.

## Decisions

1. **Observe the composed service.** Follow handlers into use cases, adapters, and the composition root. Some constructors accept optional Attempt repositories for compatibility; `ProvideCreateSubmissionUseCase`, `ProvideApplyJudgeResultUseCase`, and `ProvideGetAdminSubmissionDetailUseCase` supply them in the actual service. Alternatives rejected: inferring runtime guarantees from interfaces or test doubles alone.
2. **Keep the delta behavioral.** Requirement names describe observable rules; implementation paths and functions live only in this Evidence table. The recorded atomicity follows the transaction context through all participating repositories and the outbox publisher. It does not promise eventual delivery or exactly-once execution. Alternative rejected: converting intended architecture into unverified behavior.
3. **Keep current read semantics distinct.** Personal detail uses a single current-Attempt read; personal history and staff detail use separate reads. User-facing summary total is the stored result count; staff detail also exposes the separately reported dataset total. Alternatives rejected: asserting a shared snapshot for all reads or inventing dataset totals from executed results.
4. **Preserve observed limitations.** Validation precedes stale/duplicate guards, and the first terminal result wins. Cooldown has no rollback release. The baseline does not correct these rules or add Premium checks. Alternative rejected: documenting a desirable future policy as current behavior.
5. **Review without changing source.** Use existing tests and direct evidence review; add no tests or tooling to the repository. Verification runs in an isolated copy because `scripts/verify.sh` creates environment files and installs/builds website dependencies. Test outcomes establish local checks only, with opt-in integrations reported separately.

## Risks / Trade-offs

- [Documenting a bug can be mistaken for endorsing it] → Findings explicitly separate observed behavior from future remediation; all 22 requirements describe this checkout only.
- [Documentation can drift from implementation] → Evidence names concrete functions, reviews are grouped in `tasks.md`, and no unconfirmed behavior becomes a requirement.
- [Passing local tests can overstate integration assurance] → Opt-in PostgreSQL/Redis tests require dedicated services and are not presumed to run during normal verification; no production, end-to-end, or delivery acceptance claim is made.
- [Project CLI configuration warnings] → The CLI reports that artifact-specific `rules` are strings rather than arrays and ignores them. Their relevant documentation constraints are followed manually; configuration is outside the permitted edit scope.
