## Decisions

### Accepted policy from ADR-0006

Use dedicated Goose v3.30.0 tooling, independent SQL-only migrations and database-local histories, reviewed immutable releases, verified targets, and serialized forward execution. A migration file normally commits its DDL and version together. Seeds are explicit and large compatibility backfills run in separately verified resumable batches. Local startup requires verification of all three databases and each service performs a read-only schema check. Managed use requires separate migration credentials, protected release serialization, and a rehearsed compatible rollback target. ADR-0001, ADR-0002, and ADR-0003 continue to govern Problem locking, testcase object reclamation, and Worker cache generations. [ADR-0006](../../../docs/architecture/adr/0006-schema-migration-policy.md) · [ADR-0003](../../../docs/architecture/adr/0003-worker-testcase-cache-generations.md)

### Proposed implementation

**Capture and compare the schemas.** Replay the exact legacy constructor sequence from the inspected revision on fresh disposable PostgreSQL 15.6, including the explicit Attempt alteration. Capture the outcome of every migration call because the current constructors discard errors. Save a normalized schema-only dump and a deterministic PostgreSQL catalog inventory for each owner. Compare the legacy and migrated databases for tables, columns and types, nullability, defaults, sequence properties and ownership by column, primary and foreign keys, uniqueness, referential actions, and index definitions, ordering, predicates and validity. Compare service objects exactly after removing volatile catalog identifiers and identifying expected bootstrap and migration metadata. Verify role and object privileges separately. The catalog comparison must settle physical relationships, including testcase metadata and the query-level current-attempt reference. A discrepancy blocks cutover until it is understood and resolved within parity scope.

**Own the three sequences.** Start each of `services/auth/migrations/`, `services/problem/migrations/`, and `services/submission/migrations/` with `00001_initial_schema.sql`. Keep one transactional Up section per file and place schema and necessary compatibility data in reviewed versions. Leave Down absent for the initial files. A future Down requires a verified reversal and stays outside deployment, and any future nontransactional file requires a reviewed recovery procedure and a disposable failure rehearsal. Keep fixtures, curated tags and the existing format backfill outside initial DDL.

**Package and pin the runner.** Use a dedicated one-shot executable built around the tagged Goose Provider in an isolated tooling module outside the application workspace, with a separate pinned Go 1.26 toolchain. Verify the upstream Goose v3.30.0 distribution checksum or OCI digest, architecture, and PostgreSQL CLI behavior on disposable PostgreSQL first. Record the Goose source/module pin and pin the actual runner artifact by checksum or OCI digest per supported platform. Local, CI and future protected releases consume the verified artifact and migration bundle. The stock CLI has no configured lock and its `status` can initialize history. The Provider fits one process and one database session. Its convenience methods, including `UpTo` via `HasPending`, can touch the version table before its own session locker runs. All DB-facing Goose calls therefore sit inside the runner's explicit guard. [Goose v3.30.0 release](https://github.com/pressly/goose/releases/tag/v3.30.0) · [Tagged status](https://github.com/pressly/goose/blob/v3.30.0/status.go) · [Tagged Provider](https://github.com/pressly/goose/blob/v3.30.0/provider.go) · [Tagged Go module](https://github.com/pressly/goose/blob/v3.30.0/go.mod)

**Validate the bundle and intended target.** Before any database write, validate the immutable bundle against a trusted manifest containing the source revision, executable pin, owner mapping, ordered file names, SHA-256 hashes, and each target version. CI compares released files to a trusted release record outside the candidate checkout. Execute the same verified bytes the validator inspected. Reject gaps, duplicates, reordered or rewritten released files, unapproved content and unversioned execution. Require an explicit independently provisioned environment and instance identity, approved endpoint, DB and schema mapping, and dedicated login. Local provisioning binds identity to the exact Docker context/project or isolated fixture, the PostgreSQL instance and database identities, and the approved storage. Check the connected target with catalog queries for database, schema, owner, effective/session role and writable primary. Names or the DSN alone are insufficient. Restrict the search path and use qualified catalog queries. Reject missing, ambiguous or mismatched evidence without initializing the ledger. Finalize the local identity mechanism after confirming that the migrator can read the required identity with narrow grants.

**Take the lock on the execution session.** Use a stable PostgreSQL session advisory lock per database across invocations, owners' entry points and revisions. Use an exclusive pool with a single physical connection and a connector that refuses to open a replacement once that session is established. The same backend holds the lock while checking the full history, executing SQL and updating history through the Provider, and doing the post-check. Returning a connection to this private pool must preserve the physical session and lock. Verify that behavior against the pinned driver and Provider, including the backend identity and lock ownership. Use a direct or session-affine PostgreSQL connection, bounded lock acquisition and execution, and PostgreSQL lock/statement timeouts. A contention timeout returns failure without writing. A waiting runner rechecks history and schema after it acquires the lock. An interrupted session cannot issue further statements or reconnect mid-run. A failed or uncertain run withholds activation pending reconciliation. [Provider execution source](https://github.com/pressly/goose/blob/v3.30.0/provider_run.go) · [PostgreSQL advisory locks](https://www.postgresql.org/docs/15/explicit-locking.html#ADVISORY-LOCKS)

**Validate database history and live schema.** Inspect the database-local `goose_db_version` using read-only queries under the lock. Verify ledger shape, ownership, expected bootstrap record when present, and the full ordered set of applied versions against the trusted bundle prefix. Check the live catalog against the expected schema for that prefix. Track approved file hashes outside Goose history, which records versions. Retain the bundle and target evidence before any write and record the outcome afterward. A known applied prefix requires trusted evidence that its file hashes match, even when the new checkout's schema would look identical. An authorized empty target with no application objects or history can initialize. A bootstrap-only ledger left by a failed initial file can resume when its provenance is established and the application schema is still empty. Reject stray or incompatible application objects, unmanaged non-empty databases, missing or newer versions, unknown histories and drift. At the verified target, exit successfully with unchanged schema, history and data using read-only checks.

**Provision distinct roles.** Retain DB creation in local bootstrap and provision per-owner migrator and runtime identities through an explicit local-only bootstrap path. The migrator holds ownership/DDL and ledger-write privileges only for its target. The runtime role gets its service's required DML, schema usage, sequence privileges, and ledger reads. Check effective grants and role membership, including indirect ownership and ability to assume the migration role. Verify isolation from the other service databases. Provide credentials through ignored local configuration or protected, externally supplied files, with separate credentials for migration and runtime. Logs and evidence carry redacted target identifiers, version and outcome only. The managed provisioning path and actual grants require independent Infra review. [PostgreSQL privileges](https://www.postgresql.org/docs/15/ddl-priv.html)

**Verify startup at the composition root.** Remove all eight `AutoMigrate` calls and the Attempt alteration. Check compatibility after connecting using the effective runtime role, before repository consumers, listeners or background work start. Use read-only, bounded checks of ledger and required catalog invariants, with the expected schema tied to the service build. The M1-02 build knows the initial version. Future releases must demonstrate compatibility for any explicitly supported range, including an eligible DDL-free rollback version. Keep the Wire inputs and generated injectors consistent and propagate verification failures. Seed and backfill commands use the owning service's schema check before their operations. Preserve the reconciler's safety checks and the benchmark provisioner's DDL-free path. [Canonical identity requirements](../../specs/identity-session/spec.md) · [Problem catalog](../../specs/problem-catalog/spec.md) · [Content moderation](../../specs/content-moderation/spec.md) · [Submission](../../specs/submission/spec.md)

### Operational contract draft

- **BREAKING — local startup.** The supported local launcher takes an explicit target and approved bundle. It activates services only after one verified run covers all three owners for the current checkout. Each PostgreSQL-owning service additionally checks its own database with runtime credentials. Missing or incompatible schema fails startup with an actionable redacted diagnostic.
- **One-shot migrator.** Read-only verification never initializes history. Forward execution is explicit and authorized. Exit zero requires all requested targets to pass post-checks. A nonzero result identifies refused, failed, uncertain, or unattempted databases and retains any completed outcomes. Record the revision, tool pin, hashes, target identity and before/after versions and check results in redacted run evidence.
- **NON-BREAKING — service contracts.** HTTP, gRPC, Kafka, GORM queries and transactions, authentication and authorization, and service ownership retain their current contracts. Preserve soft-delete slug behavior, testcase package privacy and immutability, and submission/rejudge Attempt correlation.

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| A successful legacy boot can conceal a failed DDL call. | Verify each call and compare the physical schema, including nullable Attempt provenance, association constraints, sequences, and delete actions. |
| A history number can match while SQL or the live schema differs. | Check released file hashes, the complete applied prefix, catalog invariants, and trusted target provenance together. |
| Session loss or a partially applied batch can leave uncertainty. | Keep DDL on the lock-owning session, retain committed progress, and require reconciliation before retry or activation. |
| A completed local job or reused infrastructure can refer to an earlier checkout or dataset. | Bind startup to fresh run evidence and use isolated local state by default. |
| A tagged cutover image can publish while the existing deploy path is unable to migrate or roll back safely. | Enforce the protected hold and keep local Compose additions outside the effective production bundle. |

## Migration Plan

### Local cutover and fixtures

1. The local launcher uses a local-only Compose overlay because the protected rollout also consumes the base Compose file. One dedicated migration service waits for healthy PostgreSQL. The runner additionally requires successful authenticated TCP connections to each provisioned database before proceeding. The three application services depend on the migration job completing successfully. Preserve the Kafka, Redis, MinIO, Envoy, JWK and Worker startup dependencies.
2. Compute the bundle identity from the current checkout's revision and verified migration bytes. Serialize local launch for the same target project through activation. Recreate the one-shot job for the invocation and verify its result against the target identity and a fresh run identifier before enabling applications. Require matching current-run verification in the local startup config, even when an old container exited successfully. Bind the supported direct Go launch path to the same fresh all-owner check and pass the matching local config or receipt. A service's own read-only check remains independent. Verify the effective protected Compose graph without the local overlay.
3. Use a fresh isolated local PostgreSQL instance or approved disposable dataset. A reset is a separate operation after exact opt-in for the Docker context, Compose project, and specific PostgreSQL volume or database. Refuse ambiguous, shared, managed or unknown inputs. Fresh fixture isolation should include Kafka topics/consumer state, Redis and MinIO, and distinguish Worker cache state. Fixed Compose container names and published ports mean a new project name alone is insufficient for a parallel stack. Prefer an isolated local Docker context or demonstrably independent resources. Any reuse requiring deletion needs separate exact approval and applicable testcase quiescence and reference checks. Record the exact approved reset scope if used. [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/) · [Local Compose](../../../docker-compose.yml)
4. Move the fixture's empty-schema assertion before Goose. Keep the validated loopback port, explicit opt-in, fixed fixture role/database identities and per-suite recreation. Before test writes, assert the expected disposable fixture identity, verified history/schema, and empty application data. Run the suites with runtime credentials after migration by a separate fixture migrator. CI must still fail on skips or zero executed suites. [Problem fixture](../../../services/problem/internal/adapter/outbound/persistence/postgres/problem_mutation_integration_test.go#L26) · [Submission fixture](../../../services/submission/internal/adapter/outbound/persistence/postgres/submission_detail_integration_test.go#L22) · [CI](../../../.github/workflows/ci.yml#L59)
5. Rehearse a clean startup, repeat migration and explicit seed runs, and rebuild the application images. Smoke-test Auth, Problem and Submit → Outbox → Kafka → Judge → Verdict, then rejudge and verify that a previous Attempt cannot change the current state. On partial success, keep committed versions with no application activation. Reinspect each target's history and schema under the guard before a safe retry of the same approved bundle. For an uncertain write or an approved nontransactional failure, require a reviewed forward repair or tested restore where forward repair is unsafe.

### Protected promotion and managed-release prerequisites

The existing tag-driven workflow publishes and deploys through App/Judge health checks and can restore the previous image/config bundle. Without schema preflight, a cutover tag can reach activation against an empty, legacy, or drifted database. Restoring a legacy image risks restarting runtime DDL. The local overlay leaves existing protected deployment wiring intact. [Protected rollout](../../../docs/DEPLOYMENT.md#normal-protected-rollout) · [Release transition](../../../scripts/deploy-release-transition.py#L137)

**Hold the cutover before promotion.** Before integrating the startup cutover into a promotable branch, the maintainer and Infra owner must demonstrate enforceable controls outside the candidate bundle. Block the cutover commit and its descendants from release eligibility on `main` and protected tags, and deny protected activation of SHA and tagged images until managed gate and rollback rehearsal evidence is verified. Cover staging if enabled, existing App/Judge entry points and manual activation controls. Publishing a development SHA is separate from eligibility. A runbook warning or manual approval alone cannot satisfy the hold. If an enforceable hold is unavailable, keep the final cutover isolated on its feature branch. This review and hold evidence are in scope. Implementing or exercising a managed migration and changing protected production configuration are outside the local cutover.

Before first managed use, protect the entire release from interleaving across all three databases and across entry points, in addition to the per-database locks. Preflight approved artifacts, instance and role identities, trusted histories, backup and recovery point, runtime and rollback schema ranges, statement and lock timeouts, and representative lock/rewrite costs. When a prior managed schema exists, rehearse the actual supported upgrade from it with representative data. An unmanaged pre-Goose target stops routine deployment and needs separately approved data-preserving adoption, backup and rehearsed recovery. Apply compatible forward migrations, verify all three targets and retain redacted evidence before App/Judge activation. Preserve Worker suspension, Kafka group verification and cross-node rollback. Rehearse compatible image rollback while leaving database versions in place. Exclude legacy runtime-DDL images from routine rollback and prohibit automatic down migrations or ledger adoption by hand. Follow Expand → Backfill/Adapt → Contract and verify a resumable backfill before switching reads or tightening constraints. Handle a later database failure without undoing prior commits. Verify actual state before resumption.
