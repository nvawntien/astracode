## Decisions

### Accepted policy from ADR-0006

Use dedicated Goose v3.30.0 tooling, independent SQL-only migrations and database-local histories, reviewed immutable releases, verified targets, and serialized forward execution. A migration file normally commits its DDL and version together. Seeds are explicit and large compatibility backfills run in separately verified resumable batches. Local startup requires verification of all three databases and each service performs a read-only schema check. Managed use requires separate migration credentials, protected release serialization, and a rehearsed compatible rollback target. ADR-0001, ADR-0002, and ADR-0003 continue to govern Problem locking, testcase object reclamation, and Worker cache generations. [ADR-0006](../../../docs/architecture/adr/0006-schema-migration-policy.md) · [ADR-0003](../../../docs/architecture/adr/0003-worker-testcase-cache-generations.md)

### Proposed implementation

**Capture and compare the schemas.** Replay the exact legacy constructor sequence from the inspected revision on fresh disposable PostgreSQL 15.6, including the explicit Attempt alteration. Capture the outcome of every migration call because the current constructors discard errors. Save a normalized schema-only dump and a deterministic PostgreSQL catalog inventory for each owner. Compare the legacy and migrated databases for tables, columns and types, nullability, defaults, sequence properties and ownership by column, primary and foreign keys, uniqueness, referential actions, and index definitions, ordering, predicates and validity. Compare service objects exactly after removing volatile catalog identifiers and identifying expected bootstrap and migration metadata. Verify role and object privileges separately. The catalog comparison must settle physical relationships, including testcase metadata and the query-level current-attempt reference. A discrepancy blocks cutover until it is understood and resolved within parity scope.

**Own the three sequences.** Start each of `services/auth/migrations/`, `services/problem/migrations/`, and `services/submission/migrations/` with `00001_initial_schema.sql`. Keep one transactional Up section per file and place schema and necessary compatibility data in reviewed versions. Leave Down absent for the initial files. A future Down requires a verified reversal and stays outside deployment, and any future nontransactional file requires a reviewed recovery procedure and a disposable failure rehearsal. Keep fixtures, curated tags and the existing format backfill outside initial DDL.

**Package and pin the runner.** Build a dedicated one-shot executable around Goose Provider v3.30.0 and its pinned pgx v5.12.0 `stdlib` driver in an isolated tooling module outside the application workspace, using a separately pinned Go 1.26 toolchain. Verify the upstream distribution checksum or OCI digest, architecture, and PostgreSQL CLI behavior on disposable PostgreSQL. Pin the actual runner artifact by checksum or OCI digest per supported platform. Use this pin in local and CI runs and retain it for future protected releases. The stock CLI has no configured lock and `status` can initialize history. The Provider's `UpTo` calls `HasPending` before its own session locker. Use only the forward `ApplyVersion` path for each verified pending version, with every DB-facing Goose call inside the runner's guard. [Goose v3.30.0 release](https://github.com/pressly/goose/releases/tag/v3.30.0) · [Tagged status](https://github.com/pressly/goose/blob/v3.30.0/status.go) · [Tagged Provider](https://github.com/pressly/goose/blob/v3.30.0/provider.go) · [Tagged Go module](https://github.com/pressly/goose/blob/v3.30.0/go.mod)

#### Single-session feasibility gate

Use a private `database/sql` handle with one open and one idle connection and no automatic expiry. Wrap the direct pgx `GetConnector` to permit one physical connection attempt to an approved endpoint, with driver host fallback disabled. Acquire a stable per-database PostgreSQL session advisory lock, return the borrowed handle to that private pool for Provider calls, and keep the physical connection alive through the post-check. Close it to end the attempt. A waiting writer rechecks history and catalog under that lock. Use bounded acquisition and execution and PostgreSQL statement and lock timeouts. [Provider execution](https://github.com/pressly/goose/blob/v3.30.0/provider_run.go) · [Pinned pgx connector](https://github.com/jackc/pgx/blob/v5.12.0/stdlib/sql.go) · [PostgreSQL advisory locks](https://www.postgresql.org/docs/15/explicit-locking.html#ADVISORY-LOCKS)

Task 1.2 proves this on disposable PostgreSQL 15.6 before the parity migrations use it. Use two small transactional test versions. Correlate `pg_backend_pid()`, server-side statement evidence, and the observer's `pg_locks` evidence across initial ledger creation, preflight reads, migration DDL, Goose version writes and the post-check. Include the pool handoff between Provider calls. Terminate that backend during a blocked migration, confirm a competitor can then acquire the lock, and confirm the first runner exits nonzero without a replacement connection, later DDL, committed changes from the interrupted file, or an activation receipt. Retain the server and client evidence. If the pinned combination fails either proof, stop at task 1.2 and report the concrete failing path. Keep the runner limited to the three owner sequences and their disposable fixtures.

#### Target identity and privileges

At first initialization of a recognized empty local cluster, the bootstrap administrator generates one instance UUID and a separate database-generation UUID for each service database. Through the control connection to the exact PostgreSQL container, it creates a single identity record per database in a bootstrap-owned schema and records the expected UUIDs, database OID, service owner, application schema and expected login in a private descriptor outside the checkout. Bind the descriptor to the selected Docker context, Compose project, PostgreSQL container/service and data mount. On normal restart, verify those bindings and reuse the enrolled identity. For intentional container replacement, verify the same enrolled project and mount and re-read the original identity through the new container's control connection before updating its binding. A missing descriptor or an existing unmanaged schema stops the workflow. Provision the CI equivalent through the job's disposable PostgreSQL service container ID, with a fresh database-generation UUID and private runner-temp descriptor for each suite. Keep the existing loopback and fixture role/database checks.

Before any write, connect only to the endpoint derived from that provisioned target. On that session compare the identity record and database OID with the independent descriptor. Check the database, application schema and ownership, session/effective migration role, and writable primary. Use a fixed search path and qualified catalog reads. Grant the target migrator only schema usage and `SELECT` on its bootstrap identity record. Give it application-schema ownership without giving it bootstrap ownership, database ownership or superuser rights. Runtime roles do not read or modify the bootstrap record. Wrong instances with the same database names, wrong fixture generations, wrong owners or any missing identity evidence fail before Goose initializes history.

#### Bundle, applied checksums and reconciliation

Build the manifest from the reviewed Git tree for committed runs. CI resolves the actual checkout SHA and retains the clean manifest, catalog snapshots and runner pin as verification artifacts. For M1-02, anchor the empty migration sequence to the inspected `7d518406bcb5acdd2be1d22b74dd199e8d065d7f` tree and verify the three paths are absent there. After the first protected release with migrations, CI obtains the prior approved tag and exact commit from the protected release record outside the candidate checkout. Read prior migration bytes from that commit's Git tree and check their names, order and hashes against the manifest retained with that immutable release's evidence. Compare the candidate with that prefix. Missing evidence for an existing released sequence fails closed.

Stage a private snapshot of the exact ordered SQL bytes and expected catalog snapshots before validating them. The canonical manifest includes the source revision, owner and target version, runner pin, ordered file paths and SHA-256 values, and each prefix catalog digest. Its SHA-256 identifies the bundle. For local edits, compare the staged inputs against the committed tree, including new files. Require explicit opt-in for that exact dirty digest against an enrolled disposable local target. A change to either the contents or the set of inputs produces a different bundle even if `HEAD` stays the same. The runner reads only the snapshot it verified. CI and protected release evidence require a clean source revision. Local receipts bind the exact bundle, target, and fresh run ID, so a changed bundle cannot reuse earlier verification.

Generate the expected normalized catalog for each prefix by applying the reviewed sequence to fresh disposable PostgreSQL 15.6 and capturing the catalog after each version. Parity validates version one against the legacy capture. Keep the expected snapshots with the reviewed migration inputs and verify their digests and reproducibility in CI. Prefix zero expects an empty application schema. Keep the bootstrap record and Goose ledger outside the application catalog comparison and validate each separately. Normalize volatile identifiers and sequence current values while retaining sequence definitions, columns, constraints and indexes. Compare the live catalog under the lock before advancing and after each migration. A matching version with a different schema or different applied bytes fails verification.

Keep the enrollment descriptor, per-target journal and content-addressed manifests in an owner-only state directory outside the repo under `${XDG_STATE_HOME:-$HOME/.local/state}/astracode/migrations`. Use a directory per enrolled target. The Compose migrator mounts that directory and the direct launcher uses the same directory. CI uses a private per-suite runner-temp directory and exports redacted proof with the job results. Under the database lock, atomically write and sync an intent before each Provider call, including target UUIDs, prior verified version, intended version, bundle digest and file hash. Sync the file and parent directory before allowing writes. After observing the successful ledger version and matching catalog, persist a completion record for that version and hash. At exact target, check the ledger, journal and catalog read-only and leave the DB unchanged. A missing or inconsistent journal for applied versions blocks migration.

If the process loses the session or commit acknowledgement, leave the intent for reconciliation and invalidate the run's activation receipt. After reacquiring the lock, an explicit reconciliation of the same exact bundle may confirm the old prefix or the intended prefix using actual ledger and catalog evidence, including a valid version-zero-only ledger left by initialization. Record the confirmed result and resume verified pending versions only. Missing provenance, a catalog mismatch or an unexpected version keeps activation blocked. Earlier committed versions in other databases remain applied. Repair must be reviewed and forward-only unless a tested restore is necessary. Future managed provisioning must supply its own protected endpoint/instance enrollment and durable journal and release evidence accessible to authorized runners across hosts. Managed adoption and that provisioning are outside M1-02's local deliverable.

**Provision distinct roles.** Retain DB creation in local bootstrap and provision per-owner migrator and runtime identities through an explicit local-only bootstrap path. The migrator holds ownership/DDL and ledger-write privileges only for its target. The runtime role gets its service's required DML, schema usage, sequence privileges, and ledger reads. Check effective grants and role membership, including indirect ownership and ability to assume the migration role. Verify isolation from the other service databases. Provide credentials through ignored local configuration or protected, externally supplied files, with separate credentials for migration and runtime. Logs and evidence carry redacted target identifiers, version and outcome only. The managed provisioning path and actual grants require independent Infra review. [PostgreSQL privileges](https://www.postgresql.org/docs/15/ddl-priv.html)

**Verify startup at the composition root.** Remove all eight `AutoMigrate` calls and the Attempt alteration. Check compatibility after connecting using the effective runtime role, before repository consumers, listeners or background work start. Use read-only, bounded checks of ledger and required catalog invariants, with the expected schema tied to the service build. The M1-02 build knows the initial version. Future releases must demonstrate compatibility for any explicitly supported range, including an eligible DDL-free rollback version. Keep the Wire inputs and generated injectors consistent and propagate verification failures. Seed and backfill commands use the owning service's schema check before their operations. Preserve the reconciler's safety checks and the benchmark provisioner's DDL-free path. ### Operational contract draft

- **BREAKING — local startup.** The supported local launcher takes an explicit target and approved bundle. It activates services only after one verified run covers all three owners for the current checkout. Each PostgreSQL-owning service additionally checks its own database with runtime credentials. Missing or incompatible schema fails startup with an actionable redacted diagnostic.
- **One-shot migrator.** Read-only verification never initializes history. Forward execution is explicit and authorized. Exit zero requires all requested targets to pass post-checks. A nonzero result identifies refused, failed, uncertain, or unattempted databases and retains any completed outcomes. Record the revision, tool pin, hashes, target identity and before/after versions and check results in redacted run evidence.
- **NON-BREAKING — service contracts.** HTTP, gRPC, Kafka, GORM queries and transactions, authentication and authorization, and service ownership retain their current contracts. Preserve soft-delete slug behavior, testcase package privacy and immutability, and submission/rejudge Attempt correlation.

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| A successful legacy boot can conceal a failed DDL call. | Verify each call and compare the physical schema, including nullable Attempt provenance, association constraints, sequences, and delete actions. |
| A history number can match while SQL or the live schema differs. | Check released file hashes, the complete applied prefix, catalog invariants, and trusted target provenance together. |
| Session loss or a partially applied batch can leave uncertainty. | Keep DDL on the lock-owning session, retain committed progress, and require reconciliation before retry or activation. |
| A completed local job or reused infrastructure can refer to an earlier checkout or dataset. | Bind startup to fresh run evidence and use isolated local state by default. |
| A tagged cutover image can publish while the existing deploy path is unable to migrate or roll back safely. | Enforce the protected hold and keep local Compose additions outside the effective production bundle. |
