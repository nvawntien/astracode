## Goals / Non-Goals

**Goals:** trace each behavioural requirement through binding, application decisions, mapping, and persistence where applicable; retain observable differences between public, own, staff, and internal reads; identify evidence limits explicitly.

**Non-Goals:** change code, dependencies, data, interfaces, or architecture; claim runtime acceptance from unit tests; specify behaviour owned by `content-moderation`; resolve future track or Premium policy through this baseline.

## Decisions

1. **Baseline with ADDED requirements.** No main capability spec exists (`openspec list --specs` returned `No specs found.`). The delta adds an inventory of existing behaviour; it does not propose changing that behaviour. Using MODIFIED requirements would imply an existing spec that is absent.
2. **Describe the callable boundary.** Public query validation precedes use-case normalization. Pagination rejects invalid supplied values even though direct application calls contain defensive defaults/clamping. Difficulty is case-sensitive at request binding despite later normalization. Requirements describe those observable calls rather than exposing application helpers as a separate product interface.
3. **Map existing state narrowly.** Published reads correspond to `IsHidden == false`; Hidden reads correspond to `IsHidden == true`. Deleted records are excluded by persistence default scopes. Do not infer the fuller moderation lifecycle from that boolean. Contributor remains the glossary's deprecated term because it is still enforced in code.
4. **Preserve read-surface differences.** Public statements and lists use `MapProblemToResponse(..., false)`. Own/staff lists use the private mapping; privileged detail additionally supplies update metadata. Internal metadata reads return only identity/title/slug/limits and authorize against the state they read, including potentially cached state. Replacing all of these with one desired access model would be inaccurate.
5. **Keep uncertainties out of normative claims.** Q1–Q3 remain in the proposal. Default-active tag creation is evidenced, while initially-inactive persistence is not guaranteed. Numeric limits are copied, without inferring units or execution guarantees. Curated seeding is an explicit operation, without promising deployed tag contents.

## Risks / Trade-offs

- Source-grounded requirements can still lack scenario-specific automated tests → evidence rows distinguish source review, fake-backed tests, and database execution; no tests or fixes are added by this documentation change.
- Current quirks could be mistaken for desired policy → proposal Findings retain them and future approved changes can amend the baseline.
- Name-order and newest-first queries lack tie-breakers, and list/count are separate reads → no deterministic tie order or shared-snapshot consistency is promised.
- The tag-deactivation check and update are separate operations → no concurrency guarantee is inferred from the guard.
- The configured OpenSpec artifact rules are YAML strings, which the installed CLI warns it ignores because it expects arrays → follow the read rules and user constraints manually; leave configuration untouched.
