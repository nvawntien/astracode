## Goals / Non-Goals

**Goals:** Keep observable judging rules in one ADDED-only delta, with one evidence row per requirement, including the distinction between a returned Verdict and a retryable processing error. Record default and conditional behaviour separately.

**Non-Goals:** No implementation, defect correction, new acceptance test suite, runtime guarantee inferred from an external dependency, migration, deployment, merge, or archive. The related capabilities `code-run` and `submission` are references only.

## Decisions

1. **Describe worker behaviour, including limitations.** The alternative of documenting intended architecture would misstate compile-status handling, the three-try retry loop, and package integrity checks. J08 preserves returned compile failures as COMPILATION_ERROR; J12 preserves returned executor internal-error Verdicts; J14 and J21 describe actual processing errors separately.
2. **Specify requested Sandbox limits without asserting unverified isolation.** The alternative of promising network or syscall isolation is not supported by the inspected code. The worker constructs CPU, wall-time, memory, process, and output limits; `build/sandbox/Dockerfile` pins an external executor image, installs Java 17 and Python 3, and installs Go 1.22.1. Exact C++ compiler and Python package versions are not pinned.
3. **Distinguish two caches.** J04 describes the always-used worker filesystem package cache. J16-J17 describe the optional executor-owned input cache, disabled in `workers/judge/config/config.yaml`. Neither implies authoritative upstream checksum verification or guaranteed concurrent filesystem refresh safety.
4. **Keep implementation names out of the behavioural delta.** Paths, function names, protocol details, and existing test references live here. The alternative of embedding them in requirements would couple the spec to adapters and breach the requested baseline format.
5. **Preserve the existing interfaces.** Contract classification: **NON-BREAKING**, with no interface or event-schema change and no contract draft needed. Main specs are left untouched; all 24 requirements are ADDED in the change delta. No architecture documents need updates; doc impact is confined to this change directory.

## Risks / Trade-offs

- A baseline can make a defect appear intentional. Mitigation: keep the observed rule truthful and identify candidate defects explicitly in `proposal.md`; changes to them require another change.
- Source inspection cannot certify the external Sandbox or broker at runtime. Mitigation: describe constructed limits and acknowledgement decisions, and defer isolation and replay guarantees.
- Early termination retains a prefix although the current batch may have executed more tests. Mitigation: J13 distinguishes executed batches from retained results and reports maxima over that prefix only.
- Existing documentation is not always current, including configuration descriptions. Mitigation: implementation functions and checked-in defaults determine every requirement.
