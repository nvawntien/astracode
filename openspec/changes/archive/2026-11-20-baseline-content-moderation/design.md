# Design

## Context

See `proposal.md` for motivation, findings, and unresolved cases. This document records the implementation behind the 21 requirements at source revision `728aef2`; it proposes no implementation work.

Context read: `docs/codebase/ARCHITECTURE.md` (Problem service layers and authoring), `docs/codebase/FLOWS.md` (authoring/testcase flow), `docs/codebase/DATA.md` (Problem-owned persistence/storage), and `docs/codebase/SERVICES.md` (service and website boundaries). No NFR or ADR identifier is asserted by this baseline.

## Goals / Non-Goals

**Goals:** preserve observable behavior and trace every requirement to executable source; distinguish request binding, application authorization, persistence, and website behavior.

**Non-Goals:** introduce a review workflow, repair findings, specify `problem-catalog`, or change contracts, code, architecture documents, production configuration, or main specs.

## Decisions

1. **Use an ADDED-only baseline.** The capability inventory reports `No specs found.` The new capability records existing behavior rather than introducing new runtime behavior. Recasting future product intentions as current requirements was rejected because the inspected handlers and use cases do not implement them.
2. **Record validation at its actual boundary.** Creation and update handlers bind through `pkg/response/handle.go`; constraints in `services/problem/internal/application/dto/problem.go` therefore affect externally callable behavior even where direct use-case calls bypass them. The website applies additional validation. A single idealized validation policy would incorrectly erase these differences.
3. **Treat hidden as the implemented editable state.** `entity.Problem` has visibility and deletion fields, not a review-state machine. Both newly authored drafts and later Hidden problems satisfy the Contributor mutation checks. Published items remain available in their author's detail/list, while the Contributor page renders a read-only state.
4. **Keep private package data separate from public examples.** Metadata mappers deliberately omit object keys and download URLs. Package structure uses the `^(\d+)\.(in|out)$` entry-name pattern, numeric deduplication, consecutive numbering, and ZIP entry size metadata; it does not validate decompressed payloads. The spec avoids implementation filenames and describes these archive rules behaviorally.
5. **Limit lifecycle guarantees to what is implemented.** Sequential uploads read the current version, upload a versioned object, upsert metadata, and attempt cleanup. Object storage and metadata do not share a transaction. Storage and metadata failures can leave partial state. The sequential scope also applies to problem edits, which read a problem and write its resulting content and associations.

## Capability boundaries

`problem-catalog` owns own-catalog listing (PC-15), staff-catalog listing (PC-16), privileged individual reads (PC-17), and tag taxonomy (PC-19–PC-23). PC-03–PC-06 and PC-08 cover shared list behavior. PC-15 and PC-16 define privileged tag-filter eligibility. The Contributor Workspace and Admin Console use catalog results for navigation and management actions in CM-04 and CM-12. CM-05 covers mutation authorization. CM-10 covers tag assignment to a problem, and CM-13 checks existing assignments before publication.

See the ownership trace and isolated inactive-tag reproduction in `review.md`. The reproduction is evidence for a proposal finding.

## Risks / Trade-offs

- Concurrent uploads, object/metadata failure recovery, and deleted-slug reuse in a running environment remain unverified. See the proposal for the observed source behavior and the separate PostgreSQL result for tag creation.
- The service wires cached mutation use cases: after successful update, delete, publish, or hide, they attempt submission-problem cache invalidation and ignore deletion errors (`services/problem/cmd/server/wire_gen.go`; `services/problem/internal/application/usecase/admin/problem/submission_cache.go` → `invalidateSubmissionProblemCache`).
- Existing tests cover role matrices and metadata redaction but do not establish every scenario → review task completion must cite concrete evidence and must not imply full runtime coverage.
- Glossary/future-workflow expectations differ from runtime → retain Contributor and hidden-state behavior as observed and keep future moderation states outside the requirements.
- Artifact structure and the ownership boundaries are checked explicitly during review.

## Verification Approach

- Trace each requirement and scenario to its evidence row. Check ADDED-only operations, SHALL wording, WHEN/THEN scenarios, and one Evidence row per requirement.
- Run strict OpenSpec validation and check the diff and change directory scope. Run the repository verification in an isolated checkout to keep generated files out of the review branch.
- Use existing Go role/ownership, route policy, cache, seed, and metadata-redaction tests and the website role test for their covered behaviors. The isolation and result of the focused PostgreSQL probe are documented in `review.md`.
