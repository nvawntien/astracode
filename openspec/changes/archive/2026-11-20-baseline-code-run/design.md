## Goals / Non-Goals

**Goals:** Make each observable Custom run rule traceable to a concrete function, distinguish defaults from effective configuration, and distinguish per-testcase outcomes from run-level completion.

**Non-Goals:** Runtime changes, new tests, configuration fixes, architecture redesign, or deployment verification. `judging` is outside this baseline. Main specs and other changes remain untouched.

## Decisions

1. **Baseline the complete custom-run call chain.** Submission validates and resolves Problem metadata, forwards limits through its runner, and receives synchronous results from the worker handler/use case and Sandbox adapter. Worker-only discovery would miss request limits and caller authorization. Treating the internal worker handler as a separate public request contract would also incorrectly imply that it repeats Submission validation; it does not.
2. **Specify observed behaviour, including surprising outcomes.** Preserve the compilation minimums, the timeout's position after Problem resolution, and `completed` for returned per-case failures. The alternative of specifying configured intentions would contradict executable code. Potential fixes remain findings and questions in the proposal.
3. **Keep behavioural text separate from evidence.** The delta contains only Purpose and ADDED requirements with WHEN/THEN scenarios. File/function references belong in the table below. Each requirement has one row; supporting tests supplement rather than replace source inspection.
4. **Preserve scope and interfaces.** Contract classification: **NON-BREAKING**, with no interface, schema, route, dependency, or data-model change. Documentation impact: only this change directory; none of the architecture documents above needs an update for a current-behaviour baseline. No migration, deployment, or rollback procedure is needed because runtime behaviour is unchanged.

## Risks / Trade-offs

- **Existing bugs become explicit baseline behaviour** → Keep the four findings in `proposal.md` visible; require a separate approved change to alter them.
- **Configuration can override defaults** → Label default values and normalization rules in the spec; do not claim live environment values.
- **Unit tests use test executors rather than a deployed Sandbox** → Treat them as request-construction, mapping, and use-case evidence. Source review supports untested branches; no claim that every scenario has a dedicated test or that real language execution/resource enforcement was exercised.
- **Diagnostic sanitization recognizes particular patterns** → Specify recognized prefixes/locations only, without promising complete path redaction or a diagnostic for arbitrary text.
- **Baseline drifts after source changes** → Retain the inspected revision and exact function pointers for review.
