## Context

At the design baseline `1804dc2`, the checkout contained local Compose, an SSH-based dual-node Compose deployment reference, six application image builds, and no Terraform or Kubernetes platform. At that baseline, the release workflow built from `develop`, semantic tags and manual SHA input. The legacy deployment workflow consumed semantic tags and uses App SSH plus a private jump to Judge. Reuse its contract probes, health checks, Kafka consumer-group checks and paired rollout and rollback ordering. The local migrator uses local owner credentials and is disabled in the production Compose override. The cloud path needs its own managed migration gate. [Deployment reference](../../../docs/DEPLOYMENT.md) · [Development and CI](../../../docs/codebase/DEVELOPMENT.md)

The existing application uses Envoy-verified identity, service-owned databases, a transactional Submission outbox, attempt-correlated results, and separate Kafka and gRPC judging paths. Submission has an instance-local SSE hub and a relay without row claiming. Current internal gRPC transport is plaintext and some calls rely on network trust. Preserve the existing API, event and data contracts. [Architecture](../../../docs/codebase/ARCHITECTURE.md) · [Flows](../../../docs/codebase/FLOWS.md) · [Data](../../../docs/codebase/DATA.md) · [Technical debt](../../../docs/codebase/TECH_DEBT.md)

Follow [ADR-0004](../../../docs/architecture/adr/0004-azure-topology-and-subscription-layout.md), the managed portions of [ADR-0006](../../../docs/architecture/adr/0006-schema-migration-policy.md), and the Goose CLI and startup checks in [ADR-0011](../../../docs/architecture/adr/0011-local-goose-migrations.md). The offline candidate includes the privileged executor boundary in Accepted [ADR-0012](../../../docs/architecture/adr/0012-judge-executor-trust-boundary.md) and the simplified staging operating model under Proposed [ADR-0013](../../../docs/architecture/adr/0013-staging-lifecycle-control-plane-and-identity.md). Live use of the executor requires S3 validation under ADR-0012. The Orchestrator authorized the offline simplification. ADR-0013 remains Proposed pending independent review. Primary targets are NFR-D01/D02/D04/D06. Supporting controls come from NFR-D03/D05/D07/D09, NFR-A06, NFR-F01–F03, NFR-R01/R02 and NFR-S05/S08/S09. [Quality targets](../../../docs/product/nfr.md)

## Goals / Non-Goals

**Goals**

- Render and exercise the proposed infrastructure and release controls offline with synthetic inputs. Require separate real-cloud evidence for account eligibility, recreatability, access, sizing, costs and failure recovery.
- Keep an S3 experiment and S2 staging reproducible from the same two-node definitions. Allow future S1 use of those definitions with independent state, runtime configuration and data.

**Non-Goals**

- Production activation, HA, alternative CNIs or VPN infrastructure, managed Kubernetes, Helm platform stacks, service meshes, GitOps controllers, distributed storage, and autoscaling are outside this change. Preserve the Compose development entry point and existing judge execution design.
- Full observability, capacity and contest testing, and the external backup and DR program stay with their scheduled milestones. This change needs enough recovery evidence for migration, compatible rollback and App disk reattachment.

## Decisions

### 1. Terraform roots, subscriptions and network access

Use two roots, `infra/azure/bootstrap` for S4 and `infra/azure/environment` for each environment. Keep resources together by concern in the environment root. Use reviewed non-secret variable inputs for each target. S1 is reserved for Production, S2 for Staging, S3 for temporary Testing, S4 for shared operations, and S5 for Reserve/DR. Environment apply and cleanup jobs bind the approved subscription, state, resource group and plan digest. Protect the App data disk and retained volumes against routine destroy or replacement. S3 cleanup uses its exact state and a reviewed disposable-resource inventory, with a follow-up check for leftover compute, disks, IPs and billable dependencies. S2 shutdown preserves infrastructure and data.

Bootstrap S4 with a temporary protected local state, then migrate it to its own Blob state key and verify the migrated state, lock and recovery access. Give each target an independent state key and preferably a distinct container for Entra data-plane scope. Keep backups and state in separate protected storage scopes. Use AzureRM Blob native locking, versioning and recovery controls, disable anonymous access and shared-key access, and use network-restricted endpoints. Use a restricted operator execution context to bootstrap and run Terraform. Start with an approved stable operator egress IP and a storage firewall rule for that path. Admit private endpoints and protected in-network access if required by policy or offer constraints. Assess both provider management-plane permissions and backend data-plane permissions, including distinct tenant credentials where needed. Hosted application workflows have no Terraform state access. [AzureRM backend and locking](https://developer.hashicorp.com/terraform/language/backend/azurerm)

Parameterize subscription, tenant, address ranges, region, pinned image, VM sizes and disk sizes. Retain the [candidate topology](../../../docs/architecture/deployment.md#azure-topology). Provision networking, the retained data disk, native shutdown definitions, emergency scope, Key Vault and budget before enabling compute. Use the protected saved-plan operator path described below. The candidate requires six regional vCPUs and two public IPv4s. Replacement preserves the single approved VM scope and network identity and does not use a spare VM or IP. [Azure preflight](../../../docs/evidence/m0-13-phase-a.md#azure-preflight-observations)

Disable default outbound access. Use explicit static IPv4 egress, App-only tester HTTPS, private cluster paths and private Key Vault access. Keep S4 receipt reachability separate for App and the protected publisher. Verify DNS, time, OS and k3s sources, registry and VM-agent endpoints, and approved SMTP or certificate paths. Record public IP, disk, Key Vault connectivity, storage and egress costs while VMs are deallocated. Keep 50/80/100% budget alerts. S1 and S5 compute remain inactive. [Azure outbound options](https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access)

### 2. Bootstrap, placement and runtime configuration

- Render secret-free cloud-init for the App k3s server with embedded SQLite, bundled containerd, Flannel VXLAN and built-in NetworkPolicy. Use systemd ordering and a mount precondition to check the expected managed disk and filesystem identity before k3s or the Local Path Provisioner can write to the PV path. Record and protect k3s SQLite and server-token recovery material separately. Disk initialization is an explicit fresh-disk action. Reattach rather than format an existing data disk, and rehearse node-bound PV metadata and path recovery.
- Use role labels, a Judge taint, narrow tolerations and required node affinity. Confine packaged Traefik and its ServiceLB endpoints to App and verify the placement of CoreDNS, Traefik and required node agents. Keep the API, kubelet, SSH, private gRPC and VXLAN off the public network. Scope Flannel UDP 8472 and required private node traffic to the node pair.
- Join Judge with a dedicated rotatable agent-only credential and CA verification. Generate and configure agent and server credentials independently. Deliver only the agent token through the owner-authorized infrastructure bootstrap path. The candidate is a one-time Azure Managed Run Command invoking a fixed installed bootstrap script as part of provisioning, with a protected parameter and a root-readable token file. Retain no token in Terraform, cloud-init, command output, logs or reusable command arguments, and verify access, reboot/rejoin and rotation. Keep the server token and administrator kubeconfig on App and out of Judge. Give this bootstrap transport identity no routine delivery role. [k3s token roles](https://docs.k3s.io/cli/token) · [Managed Run Command](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command-managed)
- Use an App-host runtime secret loader with managed identity and Key Vault read access limited to the required objects. Inject only each workload's own secrets, with separate registry, migration, runtime and operational credentials. Generate the Envoy JWK at runtime from the matching Auth signing key. Never reuse the development key. Encrypt Kubernetes secrets at rest and control access to secrets, mounts and rotation. Judge needs a scoped GHCR pull credential for approved packages, delivered through the cluster's image pull secret, and no Azure managed identity or Key Vault access. Confirm the package visibility and token type, expiry and revocation process. Separate the secret loader from the rollout identity. [Envoy configuration and key handling](../../../envoy/README.md)
- Pin Terraform, provider lockfiles, Azure CLI, the OS image, k3s and its bundled versions, Kustomize, validators, Action revisions and all workload and migration images. Use the current application Dockerfiles, upstream image pins where present, and official Goose v3.30.0. Record exact pins and verify checksums and compatibility in Phase A. Validate Ubuntu kernel/cgroup v2, containerd, Flannel/NetworkPolicy, Kubernetes APIs and go-judge behavior on the pinned versions in S3.

| Placement | Workloads and startup checks |
| --- | --- |
| App ingress | Traefik terminates HTTPS with staging client certificate authentication for authorized members. Give CI smoke tests a separate narrowly scoped identity. Use an approved staging hostname and certificate issuance/rotation path that does not open management or HTTP ports. Traefik sends the same-origin UI, API, SSE and avatar routes through the existing Envoy routing split. Validate forwarded scheme/client IP and SSE timeout and streaming behavior. |
| App application | Next.js, Envoy, Auth, Problem and Submission. Use the website's existing same-origin defaults in the build. Supply service endpoints, Viper config, cookie and SMTP settings, frontend origin, JWT and dependency credentials at runtime. Use existing health checks or protocol/fixture probes and Envoy configuration validation. Keep liveness local to process health to avoid cascading restart loops. Release readiness checks dependency and protocol health as well as the running digests. |
| App storage | PostgreSQL, Redis, Kafka and MinIO get separately retained PVs on the same verified App disk. Bootstrap three isolated PostgreSQL databases and managed roles on a fresh disk and run reviewed migrations before activation. Use one Kafka KRaft broker and the existing idempotent topic initialization for jobs, results and DLT. Keep Redis persistence, and retain distinct MinIO buckets and private testcase presigned downloads. Wait for backing-service protocol checks before running initialization and migrations. |
| Judge | Schedule the Worker and current go-judge image only on Judge. Keep the compiler/runtime setup, existing execution limits, initial Worker concurrency of one, bounded executable memory-backed work volumes and ephemeral testcase cache, writable by Worker and read-only for the executor. Preserve the cache generation and active-reader rules. Use private Worker-to-executor gRPC and existing request-level fixture probes. Benchmark CPU, memory, disk, burst behavior and platform overhead before fixing final requests, limits, cache retention and VM sizes. |

Use default-deny NetworkPolicies with explicit paths for ingress, Envoy, DNS, backing services, Submission-to-Worker, Worker-to-Problem, Kafka, MinIO and Worker-to-executor. Before either node starts k3s, install host firewall rules that drop Pod-originated IMDS, link-local metadata and management traffic, including forwarded traffic from the local CNI and overlay. Restrict App host IMDS callers to the protected systemd service accounts that need them. Keep host credential directories, kubelet credentials and runtime sockets unmounted, disable automatic workload API-token mounting, and reject host namespaces. App root and the host-installed poller and loader are trusted. An Azure managed identity is scoped to the VM. Separate client IDs limit permissions on Azure operations and do not isolate processes that can access host IMDS. [Azure VM managed identity boundary](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-use-vm-token)

Constrain the privileged go-judge exception to the platform-owned Judge workload, pinned approved digest, dedicated namespace and node. That exception implements the trust model accepted in [ADR-0012](../../../docs/architecture/adr/0012-judge-executor-trust-boundary.md). Keep its cache read-only and work space bounded. Omit explicit host device, credential-directory and runtime-socket mounts and host namespaces. Only Worker may reach the private executor endpoint. Enforce network and namespace limits for submitted processes and deny their access to any metadata or management path. Judge has no Azure managed identity and no Key Vault role. Verify both ordinary Pod isolation and actual sandbox behavior on S3 before opening S2. For staging, document the isolated VNet and private-network plaintext transport decision for cross-node gRPC and testcase download. Escalate a failed isolation or transport requirement for review with tester access closed. [ADR-0003 cache generations](../../../docs/architecture/adr/0003-worker-testcase-cache-generations.md) · [k3s networking](https://docs.k3s.io/networking/networking-services)

Apply the fixed host-installed rollout procedure to the release's allowed inputs. Keep the Kubernetes service accounts, RBAC, NetworkPolicies, namespaces, node placement, bootstrap, security-sensitive manifest templates and their allowlist under the infrastructure operator. The rollout identity may update only its named workload controllers and designated non-secret configuration, and create bounded migration Jobs with approved templates. It receives no Secret reads, arbitrary Pod creation, exec, port forwarding, role binding or policy modification. Enforce the platform-owned allowlist on rendered manifests and on admitted Pod templates, Pods and covered subresources through native Kubernetes ValidatingAdmissionPolicy configured to fail closed. The trusted host activation service updates the short-lived admission parameters for named workload digests after verifying the protected App record. The rollout identity cannot write those parameters. Reject changes to workload kind, namespace, service account, commands or guard mounts, node placement, host namespaces, security contexts, host paths and secret references except for the specific platform-approved shape of each workload. Block unapproved init, sidecar and ephemeral containers. The release bundle supplies data to the trusted renderer. It cannot define or relax the rules used to admit it. [Kubernetes Validating Admission Policy](https://kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)

### 3. Release, approval and private deployment transport

Keep the existing exact-source CI, immutable GHCR publication and separate S4 canonical receipt. Build and verify an isolated, non-promotable rehearsal bundle for each exact reviewed S3 candidate. Protect S2 deployments and rehearsals under separately scoped native GitHub Environment Required Reviewers. Freeze the operation, target, source and digest before approval. Restrict the workflow to protected refs, disable self-review and bypass, reject reruns without new review, and serialize per environment. Keep publishers outside delivery, power and Terraform authority.

Use the fixed App host rollout entry point through narrowly scoped Azure VM Run Command if live preflight confirms support. Its VM-agent channel avoids public SSH and Kubernetes access. The Azure role grants guest execution on the exact App VM and the protected job must be trusted for that authority. Restrict federation to the protected workflow and environment and grant only the actions required by the selected command API. Keep role assignments, VM power and access to Judge out of that job. Untrusted refs and unapproved jobs must fail to acquire the effective grant. Report a blocker if the target cannot support a secure automated path.

The trusted App reads the immutable canonical receipt for S2 and requires the exact preapproved rehearsal source/digest for S3. The host checks receipt provenance, artifact bytes and per-environment configuration before authorizing any changes. It records a deployment attempt once, verifies the current owner-approved window and both node observations, and returns sanitized observed deployment and smoke evidence. Promotion eligibility uses verified protected deployment evidence for the exact canonical release. It grants no deployment, build or power rights.

### 4. Operating window, native shutdown and infrastructure recovery

The Orchestrator records the fixed window in an existing channel. The infrastructure operator confirms the schedule on both nodes, checks the observed off interval and starts the pair manually within that approved window. The cutoff does not move with readiness. Use a bounded host-local cutoff for tester/admission and workload authorization, leaving time to drain before independent daily native deallocation. The operator can stop earlier, verifies both Azure instance views, and invokes the deallocate-only path and alerts the owner if the schedule misses either VM. Preserve the budget alerts. Fresh approval is mandatory before any cutoff change.

Terraform creation can implicitly start compute. Treat it as a separate approved infrastructure operation bound to the exact reviewed saved plan, immutable VM identities and a short deadline, with emergency authority and a scheduled shutdown check before admission. First creation has no prior off-time record. For one delete-before-create replacement, prove the same VM name, size, NICs, IPs and retained App disk within existing quota. If the operation fails with one VM absent, reconcile state, bind a fresh approval to the exact missing VM, and use a reviewed recovery plan without destroying retained resources. Keep workload admission closed until verified activation.

### 5. Managed migration, activation and rollback

**Boot and recovery gate.** Persist the last verified activation and any in-flight mutation in the App's persistent protected activation record, including the approved operation and boot generation, operation, exact release and config digests, migration artifact and all three verified owner histories, and clean drain or recovery outcome. Mark a mutation in progress before granting any authorization that can change state. Update the last verified activation only after rollout readiness and smoke succeed. An in-flight or unknown record is retained across hard shutdown and starts in recovery-required state.

1. On restart of either VM or its cluster services, start the control plane, verified backing stores and minimum management/recovery processes. Invalidate prior authorization using a new node/cluster startup epoch, and start with no cached grants. Keep testers, application processes, the Worker/executor and migration Jobs closed while the platform services on App verify the actual boot state and durable record.
2. Use a platform-owned launch guard as the supervisor for every application, judge and migrator container process, including every kubelet restart of an existing container. The trusted workload templates fix the guard, original command and read-only permit path. The host services install short-lived, authenticated permits scoped to the environment, current startup epochs of both nodes, session and operation, workload, approved image/config digest and expiry. Give Judge only access to its own permits through the private node path. The guard withholds the application or migration child until the permit matches, and terminates it on expiry or loss of authorization. A migration permit is single-use for the specific Job attempt with current preflight and writer lock. A stale desired-state object, old Job, cached grant or permissive owner version check grants no execution. Treat an unconfirmed stop as a recovery condition. The executor guard relies on the trusted Judge host and daemon. Admission, NetworkPolicies and the in-container guard provide no independent protection against a compromised daemon.
3. For a clean restart, verify the last approved release, drain and exact all-owner history, then issue fresh runtime permits for that release without rerunning migrations. For a partial migration or candidate rollout, keep DDL, outbox relay, result consumer and judging closed. Reconcile the actual PostgreSQL histories, stale credentials and sessions, running digests, worker state and retained work. Resume only after authorized recovery verifies a known compatible state. A separately authorized forward fix may receive a fresh migration permit after preflight and fencing. Issue runtime permits only after all three histories and termination checks pass. Check readiness and smoke before granting the tester lease. On a fresh environment the first deploy must be separately approved before any application permits issue.

**Managed rollout procedure**

1. Verify the protected session and exact release. Prepare PostgreSQL and three independent managed databases and roles before migration. Use separate migrator and runtime credentials and permissions. Grant each runtime role DML and version-read privileges in its own database. Verify fresh databases or known applied prefixes, the proposed schema and release history, target identity, backup/recovery point, migration hashes and rollback compatibility for all three before any writes. Refuse unexpected history, nonempty legacy schemas without trusted history, and drift. Reviewed seeds remain explicit.
2. Publish the current SQL sets with official Goose v3.30.0 and a managed entry point so Compose can keep its local wrapper. Use one protected environment operation and per-database PostgreSQL session advisory locks from read-only preflight through post-check. The CLI opens separate connections, so persist a database operation marker before granting run-specific migration access. Clear the marker only after the CLI exits, its DB sessions are confirmed closed and history/schema checks succeed. All entry points refuse an unresolved marker even if the advisory lock has been released. On lock loss, cancel the job, fence the stale credential and verify its sessions are gone before separately authorizing reconciliation. Use deadlines for acquisition, DDL locks and statements. Never infer safety from a Kubernetes Job terminal state alone. A partially applied sequence records per-owner results and leaves activation closed until reviewed reconciliation. [Goose v3.30.0 CLI](https://github.com/pressly/goose/blob/v3.30.0/cmd/goose/main.go)
3. Quiesce judging and affected application traffic for protected rollout, following the existing Worker suspension and group-empty checks. For Submission, scale to zero and verify the prior Pod UID's containers and relay actually stopped on the healthy App node before starting the replacement. A terminating Pod, lost node, forced API deletion or stale status cannot authorize replacement. Require the same checks on rollback and reopen the edge only after all workloads report readiness, the private Problem contract probe passes, and the exact candidate passes the smoke suite.
4. Roll back only to a previously verified DDL-free release compatible with the live schema, restoring App before its matching Judge. Keep schema versions and current secrets. Current `pkg/schema/startup.go` requires exact version equality, so rehearse the ≤15-minute rollback between two releases with the same schema and explicitly test refusal of a previous release after a version advance. A release that advances the schema needs a separately verified rollback artifact whose startup checks accept the resulting versions or a reviewed recovery path before approval. If an accepted rollback requirement cannot be met, fail closed and bring it to review. Schema repair uses a reviewed forward fix or restore, with no automatic down migration.

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| A single App node and App disk carry control plane and data dependencies. | Keep startup fail-closed on the mount. Rehearse reattachment and preserve metadata and pre-migration recovery points. |
| Private VXLAN does not encrypt cluster traffic and privileged execution resides on Judge. | Limit tenancy and permitted paths, check staging transport and credential isolation in S3 and S2, and block exposure if a boundary fails. |
| Tenant or offer constraints may invalidate state access, native shutdown, VM-agent delivery, OIDC, region, VM SKUs, public IPs, Key Vault or budget delivery. | Verify permissions, availability, estimated cost and binding in read-only preflight. Escalate an ineligible design to the Orchestrator and use ADR review for any change to the architecture. |
| A partial rollout can leave a schema ahead of the last image or a valid official job pending. | Record actual per-owner versions and retained attempt state. Prevent automatic application activation, destructive rollback and stale takeover. |
| Azure control-plane delays and actual charges can fall outside estimates. | Keep operation deadlines, verify and retry uncertain VM operations, verify power states, and wait for cost data before closing Phase B. |

**Phase A** builds the IaC, bootstrap, workload, managed migration and release/lifecycle assets using synthetic configuration. Verify `terraform fmt -check -recursive`, per-root `terraform init -backend=false`, `terraform validate` and provider-mocked `terraform test` where supported. Render and check cloud-init/systemd, use `kustomize build` and strict manifest schemas including pinned k3s and Traefik APIs, and run a disposable local rollout and failure and infrastructure-recovery regression tests. Run `actionlint`, `shellcheck`, shell syntax checks, existing CI coverage and the repository verifiers. Downloads may fetch pinned tooling and public schemas. Phase A evidence covers structure, local behavior and control logic.
