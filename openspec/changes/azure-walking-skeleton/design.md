## Context

The checkout contains local Compose, an SSH-based dual-node Compose deployment reference, six application image builds, and no Terraform or Kubernetes platform. The release workflow builds from `develop`, semantic tags and manual SHA input. The legacy deployment workflow consumes semantic tags and uses App SSH plus a private jump to Judge. Reuse its contract probes, health checks, Kafka consumer-group checks and paired rollout and rollback ordering. The local migrator uses local owner credentials and is disabled in the production Compose override. The cloud path needs its own managed migration gate. [Deployment reference](../../../docs/DEPLOYMENT.md) · [Development and CI](../../../docs/codebase/DEVELOPMENT.md)

The existing application uses Envoy-verified identity, service-owned databases, a transactional Submission outbox, attempt-correlated results, and separate Kafka and gRPC judging paths. Submission has an instance-local SSE hub and a relay without row claiming. Current internal gRPC transport is plaintext and some calls rely on network trust. Preserve the existing API, event and data contracts. [Architecture](../../../docs/codebase/ARCHITECTURE.md) · [Flows](../../../docs/codebase/FLOWS.md) · [Data](../../../docs/codebase/DATA.md) · [Technical debt](../../../docs/codebase/TECH_DEBT.md)

Follow [ADR-0004](../../../docs/architecture/adr/0004-azure-topology-and-subscription-layout.md), the managed portions of [ADR-0006](../../../docs/architecture/adr/0006-schema-migration-policy.md), and the Goose CLI and startup checks in [ADR-0011](../../../docs/architecture/adr/0011-local-goose-migrations.md). Primary targets are NFR-D01/D02/D04/D06. Supporting controls come from NFR-D03/D05/D07/D09, NFR-A06, NFR-F01–F03, NFR-R01/R02 and NFR-S05/S08/S09. [Quality targets](../../../docs/product/nfr.md)

## Goals / Non-Goals

**Goals**

- Render and exercise the proposed infrastructure and release controls offline with synthetic inputs. Require separate real-cloud evidence for account eligibility, recreatability, access, sizing, costs and failure recovery.
- Keep an S3 experiment and S2 staging reproducible from the same two-node definitions. Allow future S1 use of those definitions with independent state, runtime configuration and data.

**Non-Goals**

- Production activation, HA, alternative CNIs or VPN infrastructure, managed Kubernetes, Helm platform stacks, service meshes, GitOps controllers, distributed storage, and autoscaling are outside this change. Preserve the Compose development entry point and existing judge execution design.
- Full observability, capacity and contest testing, and the external backup and DR program stay with their scheduled milestones. This change needs enough recovery evidence for migration, compatible rollback and App disk reattachment.

## Decisions

### 1. Terraform roots, subscriptions and network access

Use two roots, `infra/azure/bootstrap` for S4 and `infra/azure/environment` for each environment. Keep resources together by concern in the environment root. Use reviewed non-secret variable inputs for each target. S1 is reserved for Production, S2 for Staging, S3 for temporary Testing, S4 for shared operations, and S5 for Reserve/DR. Environment apply and cleanup jobs bind the approved subscription, state, resource group and plan digest. Protect the App data disk and retained volumes against routine destroy or replacement. S3 cleanup uses its exact state and a reviewed disposable-resource inventory, with a follow-up check for leftover compute, disks, IPs and billable dependencies. S2 shutdown preserves infrastructure and data.

Bootstrap S4 with a temporary protected local state, then migrate it to its own Blob state key and verify the migrated state, lock and recovery access. Give each target an independent state key and preferably a distinct container for Entra data-plane scope. Keep backups and state in separate protected storage scopes. Use AzureRM Blob native locking, versioning and recovery controls, disable anonymous access and shared-key access, and use network-restricted endpoints. Use a restricted operator execution context to bootstrap and run Terraform. Start with an approved stable operator egress IP and a storage firewall rule for that path. Admit private endpoints and protected in-network access if required by policy or offer constraints. Assess both provider management-plane permissions and backend data-plane permissions, including distinct tenant credentials where needed. Hosted application workflows have no Terraform state access. [AzureRM backend and locking](https://developer.hashicorp.com/terraform/language/backend/azurerm)

Parameterize tenant and subscription references, address ranges, region, OS image version, App/Judge SKUs and disk sizes. ADR-0004's first candidates are Southeast Asia, Ubuntu 24.04 LTS x86-64, App `Standard_B2as_v2`, Judge `Standard_B2als_v2` and Standard SSD LRS with 64 GiB for each OS disk and staging App data. Verify candidates and fallbacks in order against offer restrictions, quota, availability, cost, measured latency and headroom. Keep both VMs in the same region. Compare sustained judging with B-series burst credits and non-burstable alternatives. Validate the environment plan against its exact logical target before any apply. Provision the S2 operations controller and its durable store with compute disabled in the first reviewed plan. Before applying the approved compute plan, arm a bounded owner-approved startup against the exact VM targets. Terraform VM creation can power on compute, so use the same watchdog and admission controls during provisioning.

Create environment resource groups, a VNet, App and Judge subnets and NICs, narrow NSGs, two VMs, a separately managed App data disk, Key Vault and scoped identities. Start the S3 egress comparison with Standard static IPv4 on App for restricted HTTPS and explicit outbound, and on Judge for outbound with every unsolicited Internet inbound path denied. Disable default outbound access and keep node and overlay traffic on private IPs. NAT Gateway and a Standard Load Balancer outbound rule provide other explicit paths, with additional service charges or configuration. Use the lowest-cost candidate that passes security and quota checks. Record DNS and time, OS and k3s sources, registry and Azure endpoints, and approved SMTP/certificate paths. Apply host and workload egress controls. Inventory fixed and variable charges including the operations controller, storage, disks, IPs and data transfer even while VMs are off. Apply or verify 50/80/100% subscription budgets, recipient delivery and weekly burn-rate review under the corresponding owner authorization. Subscription budget verification does not activate S1 or S5 compute. [Azure outbound options](https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access) · [Azure budget alerts](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets)

### 2. Bootstrap, placement and runtime configuration

- Render secret-free cloud-init for the App k3s server with embedded SQLite, bundled containerd, Flannel VXLAN and built-in NetworkPolicy. Use systemd ordering and a mount precondition to check the expected managed disk and filesystem identity before k3s or the Local Path Provisioner can write to the PV path. Record and protect k3s SQLite and server-token recovery material separately. Disk initialization is an explicit fresh-disk action. Reattach rather than format an existing data disk, and rehearse node-bound PV metadata and path recovery.
- Use role labels, a Judge taint, narrow tolerations and required node affinity. Confine packaged Traefik and its ServiceLB endpoints to App and verify the placement of CoreDNS, Traefik and required node agents. Keep the API, kubelet, SSH, private gRPC and VXLAN off the public network. Scope Flannel UDP 8472 and required private node traffic to the node pair.
- Join Judge with a dedicated rotatable agent-only credential and CA verification. Generate and configure agent and server credentials independently. Deliver only the agent token through the owner-authorized infrastructure bootstrap path. The candidate is a one-time Azure Managed Run Command invoking a fixed installed bootstrap script as part of provisioning, with a protected parameter and a root-readable token file. Retain no token in Terraform, cloud-init, command output, logs or reusable command arguments, and verify access, reboot/rejoin and rotation. Keep the server token and administrator kubeconfig on App and out of Judge. Give this bootstrap transport identity no routine delivery role. [k3s token roles](https://docs.k3s.io/cli/token) · [Managed Run Command](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command-managed)
- Use an App-host runtime secret loader with managed identity and Key Vault read access limited to the required objects. Inject only each workload's own secrets, with separate registry, migration, runtime and operational credentials. Generate the Envoy JWK at runtime from the matching Auth signing key. Never reuse the development key. Encrypt Kubernetes secrets at rest and control access to secrets, mounts and rotation. Judge needs a scoped GHCR pull credential for approved packages, delivered through the cluster's image pull secret, and no Azure managed identity or Key Vault access. Confirm the package visibility and token type, expiry and revocation process. Separate the secret loader from the rollout identity. [Envoy configuration and key handling](../../../envoy/README.md)
- Pin Terraform, provider lockfiles, Azure CLI, the OS image, k3s and its bundled versions, Kustomize, validators, Action revisions and all workload and migration images. Use the current application Dockerfiles, upstream image pins where present, and official Goose v3.30.0. Record exact pins and verify checksums and compatibility in Phase A. Validate Ubuntu kernel/cgroup v2, containerd, Flannel/NetworkPolicy, Kubernetes APIs and go-judge behavior on the pinned versions in S3.

### 3. Release, approval and private deployment transport

Publish after all required CI checks for the exact merged `develop` SHA, including strict OpenSpec and applicable security checks. Reuse the current test, integration fixture, gateway, Compose, script and image jobs and their required status names. Untrusted PRs receive read-only build and validation permissions. Avoid branch-wide cancellation or pending-run replacement across different release commits. Key release verification and retries by full commit SHA, reconcile skipped or interrupted publish events against passing merges, and serialize retries for one SHA. Add the migration image to the existing build matrix and pin dependency images in the release lock as well.

Publish a versioned OCI release bundle and treat its digest as the release identity. The bundle binds source SHA, six application image digests, dependency image digests, Kustomize inputs and revision, migration image digest, per-owner migration hashes and target versions, and CI evidence for that SHA. Make the full-SHA lookup write-once, prevent conflicting republish or replacement, and expose the release for selection only after the whole bundle verifies. Keep staging acceptance evidence separately keyed to that bundle digest. Runtime config is supplied by the target overlay and secret loader. The build does not consume environment-specific website URLs.

Use separate protected GitHub environments for startup/extension and deploy/rollback. The owner is the sole lifecycle reviewer and either designated maintainer can review release operations. Scope OIDC to the repository and protected environments, restrict deployment branches and tested workflow refs, and disable administrator bypass and self-review. Attach approval to the exact operation, session generation, release digest or requested deadline. Where an approver originates a request, use a separate authorized member to review the request details and dispatch the protected run so the workflow initiator and approver are distinct. Verify actual plan, visibility, branch restrictions, role membership, cancellation and access controls in Phase B. If required reviewers are unavailable, the fallback is a protected approval-request PR with role-specific CODEOWNERS, approval of the exact head, stale-review dismissal, independent reviewer and disabled bypass. A trusted post-merge workflow verifies the accepted review and immutable request, then submits the same one-use operation ticket through separately scoped identity. Verify the fallback before it can grant cloud access. [GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) · [GitHub OIDC for Azure](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-azure)

Recommend an outbound pull from App through a small deployment service installed at bootstrap. The GitHub-hosted workflow uses Azure CLI with OIDC to submit and watch a scoped operation through an Entra-authenticated HTTPS controller in Azure. The controller offers only typed session and release operations, validates audience, issuer and per-action caller roles, and passes only a versioned operation ticket and status. Backing Blob state is network-restricted and independent of the VMs. App polls outbound using its own scoped identity, resolves the approved release by digest and runs the installed deploy procedure against the local API using a purpose-specific identity. It reports bounded, sanitized status. Tickets contain no scripts, secrets or arbitrary Azure or cluster commands. Separate controller deployment and identity administration from workflow and runtime roles. Require admission checks on rendered manifests and a tightly scoped fixed rollout role, even for approved releases. The platform-controlled workload base and policies constrain use of privileged Judge workloads and prevent candidate bundles from changing cluster RBAC, API exposure or the host bootstrap.

| Transport considered | Trade-off |
| --- | --- |
| App outbound pull through the session controller | Uses the same small control service already needed for independent expiry. Keeps Kubernetes API and SSH private and avoids granting the hosted workflow guest shell access. Adds a controller/poller protocol and a protected control HTTPS interface. |
| Self-hosted runner on App or another private host | Provides direct private access. App-hosted jobs would execute workflow code on the data node and disappear when App is deallocated. A separate ephemeral runner avoids co-location but adds compute, runner isolation and startup overhead. |
| Azure VM Action Run Command for routine delivery | Reaches the private host without public SSH, with little standing runtime cost. It grants elevated arbitrary guest execution and has limited cancellation, so reserve guest-command access for protected infrastructure bootstrap/recovery and exclude it from routine deployment. [Action Run Command restrictions](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command) |

**NON-BREAKING operations contracts.** The new control interface has a versioned schema. A request is `schemaVersion, environment, operation, requestId, approvalRef` with the expected `sessionGeneration` for an existing session and either `releaseDigest` for deploy/rollback or `requestedExpiry` for extension. Duplicate request IDs return the existing outcome only for the same payload and scope. Status reports generation, phase, timestamps, release and sanitized outcome. Full deploy evidence binds approved operation, bundle digest, observed digests, migration versions, readiness and smoke outcomes. No changes to AstraCode API routes, proto, identity claims, Kafka messages or persistence ownership.

Future promotion resolves a protected semantic tag to one successful staging record and its immutable bundle. A `main` merge or tag does not build or substitute the images. Exercise tag-to-bundle, evidence matching, maintainer approval and contest-freeze guards using a non-deploying eligibility path. Keep production activation, credentials and live deployment outside M0-13. Keep the legacy production scripts as reference and protect or retire the legacy tag consumer before treating staged releases as promotable.

### 4. Durable staging session and shutdown

Use an Azure Functions timer and HTTPS handler on one consumption-based controller, with durable Blob records in S2 outside the VMs. Flex Consumption with VNet integration is the candidate for private backing storage. Size and price the controller and its storage in S3, and verify Entra auth and hosting/region eligibility. Define start and status through the controller so Actions orchestrates startup using Azure CLI and no other routine identity writes VM power state. The independent timer reconciles every minute from persisted deadlines on each run, including after missed ticks. A GitHub-only expiry workflow or a fixed daily VM shutdown cannot enforce a durable per-session deadline and recovery. [Functions timer triggers](https://learn.microsoft.com/azure/azure-functions/functions-bindings-timer) · [Functions networking](https://learn.microsoft.com/en-us/azure/azure-functions/functions-networking-options)

1. **Off → Starting.** Persist the generation, owner approval, boot deadline and expected VM targets before submitting any power operation. Serialize through Blob conditional writes and record per-VM intents before ARM calls. The controller checks both Azure states and App-reported k3s/required service readiness. An empty environment permits the separately approved first deployment during the boot allowance. Tester access opens only when both nodes and required services are verified. Reject a second start against an existing or unresolved generation.
2. **Starting → Ready.** On a routine restart, verify the last approved active release and its actual schema and drain record. Restore the previously stopped workloads for that same release without choosing a new release or applying schema changes. Keep unresolved operations behind the admission gate until authorized reconciliation. Start the one-hour clock at recorded readiness. Use UTC for persisted times and an explicit Asia/Ho_Chi_Minh daily off window. The review candidate is 00:00–12:00 local time. Admit startup only if bounded boot, the full ready session and the shutdown margin fit before the off window. Verify time deallocated from both actual VM states. Prove startup and drain deadlines in S3 before setting S2 defaults. An extension needs new owner approval against the same generation and cannot revive expired or draining state.
3. **Admit one change.** Use per-generation conditional transitions for deployment, rollback, migration and cleanup. Reserve a bounded operation window that fits the remaining boot/session time, with cancellation, reconciliation and shutdown margin. Recheck generation, request, deadline, approval and the contest freeze before a planned change. A freeze never prevents safety shutdown. Adopt/reconcile an accepted operation if its GitHub run exits, and mark unknown outcomes explicitly. A lost controller or App lease stops new mutations. The expiry controller accounts for an outstanding operation even while it owns the exclusive cleanup path.
4. **Ready or Starting → Draining.** An App-side access gate enforces a short-lived lease capped by the durable deadline and fails closed on missing or stale state. Keep the timer independent of ingress and App agents. Close tester admission at expiry, including new official submissions, rejudges, Run Code and other writes. Within the drain deadline, allow accepted work to settle, stop the Worker and verify Kafka group membership and offsets, then stop Submission after the result consumer and outbox relay settle or have a recorded durable pending state. Compare accepted attempt state, outbox, Kafka lag/offsets, DLT and unapplied results. In-flight interactive runs can terminate after the bounded drain. Preserve official work for redelivery or operator reconciliation and verify existing attempt guards on restart. Unknown state fences tester access on the next boot. The known outbox and DLT limitations remain tracked by their existing work.
5. **Draining → Off or Recovery required.** When drain completes or its hard deadline expires, automatically deallocate both VMs without removing disks. Poll Azure instance view for `PowerState/deallocated` on each VM. Treat a late start, timeout or unknown response as outstanding work: retain long-running operation identity when available, settle or reconcile it before declaring Off, and repeat deallocation of either live VM. Record unresolved work and alert maintainers if confirmation misses the cleanup deadline, with retries and escalation independent of GitHub. Alert on missed controller heartbeats or failure to meet the off-time floor. A recovered controller replays reconciliation from durable state and never grants tester admission from stale readiness.

### 5. Managed migration, activation and rollback

1. Verify the protected session and exact release. Prepare PostgreSQL and three independent managed databases and roles before migration. Use separate migrator and runtime credentials and permissions. Grant each runtime role DML and version-read privileges in its own database. Verify fresh databases or known applied prefixes, the proposed schema and release history, target identity, backup/recovery point, migration hashes and rollback compatibility for all three before any writes. Refuse unexpected history, nonempty legacy schemas without trusted history, and drift. Reviewed seeds remain explicit.
2. Publish the current SQL sets with official Goose v3.30.0 and a managed entry point so Compose can keep its local wrapper. Use one protected environment operation and per-database PostgreSQL session advisory locks from read-only preflight through post-check. The CLI opens separate connections, so persist a database operation marker before granting run-specific migration access. Clear the marker only after the CLI exits, its DB sessions are confirmed closed and history/schema checks succeed. All entry points refuse an unresolved marker even if the advisory lock has been released. On lock loss, cancel the job, fence the stale credential and verify its sessions are gone before separately authorizing reconciliation. Use deadlines for acquisition, DDL locks and statements. Never infer safety from a Kubernetes Job terminal state alone. A partially applied sequence records per-owner results and leaves activation closed until reviewed reconciliation. [Goose v3.30.0 CLI](https://github.com/pressly/goose/blob/v3.30.0/cmd/goose/main.go)
3. Quiesce judging and affected application traffic for protected rollout, following the existing Worker suspension and group-empty checks. For Submission, scale to zero and verify the prior Pod UID's containers and relay actually stopped on the healthy App node before starting the replacement. A terminating Pod, lost node, forced API deletion or stale status cannot authorize replacement. Require the same checks on rollback and reopen the edge only after all workloads report readiness, the private Problem contract probe passes, and the exact candidate passes the smoke suite.
4. Roll back only to a previously verified DDL-free release compatible with the live schema, restoring App before its matching Judge. Keep schema versions and current secrets. Current `pkg/schema/startup.go` requires exact version equality, so rehearse the ≤15-minute rollback between two releases with the same schema and explicitly test refusal of a previous release after a version advance. A release that advances the schema needs a separately verified rollback artifact whose startup checks accept the resulting versions or a reviewed recovery path before approval. If an accepted rollback requirement cannot be met, fail closed and bring it to review. Schema repair uses a reviewed forward fix or restore, with no automatic down migration.

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| A single App node and App disk carry control plane and data dependencies. | Keep startup fail-closed on the mount. Rehearse reattachment and preserve metadata and pre-migration recovery points. |
| Private VXLAN does not encrypt cluster traffic and privileged execution resides on Judge. | Limit tenancy and permitted paths, check staging transport and credential isolation in S3 and S2, and block exposure if a boundary fails. |
| Tenant or offer constraints may invalidate state access, Flex Consumption, OIDC, region, VM SKUs, public IPs, Key Vault or budget delivery. | Verify explicit permissions, region/offer availability, estimated cost and binding in read-only preflight. Treat an ineligible plan as a Gate 1 design issue if it cannot be solved within ADR-0004. |
| A partial rollout can leave a schema ahead of the last image or a valid official job pending. | Record actual per-owner versions and retained attempt state. Prevent automatic application activation, destructive rollback and stale takeover. |
| Azure control-plane delays and actual charges can fall outside estimates. | Keep operation deadlines, independently retry including uncertain VM operations, verify power states, and wait for cost data before closing Phase B. |

## Migration Plan

**Phase A** builds the IaC, bootstrap, workload, managed migration and release/lifecycle assets using synthetic configuration. Verify `terraform fmt -check -recursive`, per-root `terraform init -backend=false`, `terraform validate` and provider-mocked `terraform test` where supported. Render and check cloud-init/systemd, use `kustomize build` and strict manifest schemas including pinned k3s and Traefik APIs, and run a disposable local rollout and state-machine failure tests. Run `actionlint`, `shellcheck`, shell syntax checks, existing CI coverage and the repository verifiers. Downloads may fetch pinned tooling and public schemas. Phase A evidence covers structure, local behavior and control logic.

**Phase B** requires explicit project-owner authorization for each cloud operation. Map and preflight S1–S5, bootstrap S4, time a fresh S3 recreation from the start of environment provisioning through application readiness, record account/S4 prerequisites and timings separately, and measure resource footprint, costs, compatible rollback, mount recovery and security. Confirm sizing and remove the S3 experiment. Provision S2 and exercise the real approval and digest path, official submission and rejudge, realtime status and interactive Run Code, failure and shutdown cases, persistence across restart and compatible rollback. Record evidence of actual provisioning, identities, access, costs, deallocation and the NFR-D04 ≤2-hour target. Require both phases before acceptance.
