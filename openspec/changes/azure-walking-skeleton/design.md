At that baseline, the release workflow built from `develop`, semantic tags and manual SHA input. The legacy deployment workflow consumed semantic tags and uses App SSH plus a private jump to Judge. Reuse its contract probes, health checks, Kafka consumer-group checks and paired rollout and rollback ordering. The local migrator uses local owner credentials and is disabled in the production Compose override. The cloud path needs its own managed migration gate. Submission has an instance-local SSE hub and a relay without row claiming. Current internal gRPC transport is plaintext and some calls rely on network trust. Preserve the existing API, event and data contracts. ## Goals / Non-Goals

**Goals**

- Render and exercise the proposed infrastructure and release controls offline with synthetic inputs. Require separate real-cloud evidence for account eligibility, recreatability, access, sizing, costs and failure recovery.
- Keep an S3 experiment and S2 staging reproducible from the same two-node definitions. Allow future S1 use of those definitions with independent state, runtime configuration and data.

**Non-Goals**

- Production activation, HA, alternative CNIs or VPN infrastructure, managed Kubernetes, Helm platform stacks, service meshes, GitOps controllers, distributed storage, and autoscaling are outside this change. Preserve the Compose development entry point and existing judge execution design.
- Full observability, capacity and contest testing, and the external backup and DR program stay with their scheduled milestones. This change needs enough recovery evidence for migration, compatible rollback and App disk reattachment.

## Decisions

### 1. Terraform roots, subscriptions and network access

Use two roots, `infra/azure/bootstrap` for S4 and `infra/azure/environment` for each environment. Keep resources together by concern in the environment root. Use reviewed non-secret variable inputs for each target. S1 is reserved for Production, S2 for Staging, S3 for temporary Testing, S4 for shared operations, and S5 for Reserve/DR. Environment apply and cleanup jobs bind the approved subscription, state, resource group and plan digest. Protect the App data disk and retained volumes against routine destroy or replacement. S3 cleanup uses its exact state and a reviewed disposable-resource inventory, with a follow-up check for leftover compute, disks, IPs and billable dependencies. S2 shutdown preserves infrastructure and data.

Bootstrap S4 with a temporary protected local state, then migrate it to its own Blob state key and verify the migrated state, lock and recovery access. Give each target an independent state key and preferably a distinct container for Entra data-plane scope. Keep backups and state in separate protected storage scopes. Use AzureRM Blob native locking, versioning and recovery controls, disable anonymous access and shared-key access, and use network-restricted endpoints. Use a restricted operator execution context to bootstrap and run Terraform. Start with an approved stable operator egress IP and a storage firewall rule for that path. Admit private endpoints and protected in-network access if required by policy or offer constraints. Assess both provider management-plane permissions and backend data-plane permissions, including distinct tenant credentials where needed. Hosted application workflows have no Terraform state access. [AzureRM backend and locking](https://developer.hashicorp.com/terraform/language/backend/azurerm)

Parameterize tenant and subscription references, address ranges, region, OS image version, App/Judge SKUs and disk sizes. Use the selected [Azure topology](../../../docs/architecture/deployment.md#azure-topology). Validate allocation, latency, sustained CPU with B-series burst credits and measured resource headroom. Provision and verify the controller, disk, network and alerts before creating either VM. A protected saved-plan apply binds its digest, target and controller authorization with a current deadline. On S2, use the native startup approval with the exact Terraform plan binding and keep workload leases closed throughout infrastructure maintenance. Normal shutdown deallocates the existing VMs. At 6/6 regional vCPUs and 3/3 public IPv4s, replacement deletes one VM before recreating it with its original NIC and IP. Retain the App disk at LUN 0 and confirm its filesystem UUID. [Preflight](../../../docs/evidence/m0-13-phase-a.md#azure-preflight-observations) · [Operator runbook](../../../infra/azure/README.md#s2s3-vm-maintenance)

Create environment resource groups, a VNet, App and Judge subnets and NICs, narrow NSGs, two VMs, a separately managed App data disk, Key Vault and scoped identities. Retain the Standard static IPv4 on each node and the third on the controller subnet NAT Gateway. Restrict App HTTPS and deny unsolicited Internet inbound to Judge. Disable default outbound access, keep node and overlay traffic private and use private endpoints for the controller's Blob storage and runtime Key Vault. Record DNS and time, OS and k3s sources, registry and Azure endpoints, and approved SMTP/certificate paths. Apply host and workload egress controls. Inventory fixed and variable charges including the operations controller, storage, disks, IPs and data transfer even while VMs are off. Apply or verify 50/80/100% subscription budgets, recipient delivery and weekly burn-rate review under the corresponding owner authorization. Keep S1 and S5 compute inactive. [Azure outbound options](https://learn.microsoft.com/en-us/azure/virtual-network/ip-services/default-outbound-access) · [Azure budget alerts](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets)

Reattach rather than format an existing data disk, and rehearse node-bound PV metadata and path recovery.

Confine packaged Traefik and its ServiceLB endpoints to App and verify the placement of CoreDNS, Traefik and required node agents. Keep the API, kubelet, SSH, private gRPC and VXLAN off the public network. Scope Flannel UDP 8472 and required private node traffic to the node pair.
- Join Judge with a dedicated rotatable agent-only credential and CA verification. Generate and configure agent and server credentials independently. Deliver only the agent token through the owner-authorized infrastructure bootstrap path. The candidate is a one-time Azure Managed Run Command invoking a fixed installed bootstrap script as part of provisioning, with a protected parameter and a root-readable token file. Retain no token in Terraform, cloud-init, command output, logs or reusable command arguments, and verify access, reboot/rejoin and rotation. Never reuse the development key. Encrypt Kubernetes secrets at rest and control access to secrets, mounts and rotation. Judge needs a scoped GHCR pull credential for approved packages, delivered through the cluster's image pull secret, and no Azure managed identity or Key Vault access. Confirm the package visibility and token type, expiry and revocation process. Separate the secret loader from the rollout identity. [Envoy configuration and key handling](../../../envoy/README.md)
- Pin Terraform, provider lockfiles, Azure CLI, the OS image, k3s and its bundled versions, Kustomize, validators, Action revisions and all workload and migration images. Use the current application Dockerfiles, upstream image pins where present, and official Goose v3.30.0. Record exact pins and verify checksums and compatibility in Phase A. ### 3. Release, approval and private deployment transport

#### Canonical publication and transition

Run the canonical publisher on protected `refs/heads/develop` push for the exact merged SHA. Require all checks for that SHA, including strict OpenSpec and applicable security checks. Preserve existing CI coverage and status names. Put registry writes in the trusted publication job. Untrusted PRs run read-only checks with zero publish and Azure privileges. Serialize publication by SHA without canceling different commits. A protected `main` reconciliation workflow, run on a schedule or manually without a SHA input, enumerates missing receipts from the protected `develop` merge history. Its owner-reviewed lower bound includes the merge that introduced M0-13, even if that merge missed publication before the `main` workflow was registered. If validation or publication was skipped or interrupted, use the same check and build path for that exact merge revision. Require linked passing checks and merge provenance in the receipt. Failed checks never authorize publication.

The OCI bundle binds source SHA, six application images, dependency image digests, Kustomize revision and inputs, the migration image plus per-owner migration hashes/versions, and CI evidence. Create the canonical commit-to-bundle receipt only after verifying the entire bundle. Use a separate S4 release-records scope with conditional first-write and immutable retention, outside the Terraform state and backup scopes. Give the trusted publisher create access there only and the controller read access. Verify write-once behavior, tenant/RBAC and network reachability before enabling the publisher. A retry adopts and verifies the first receipt. Conflicting content, missing evidence or interrupted builds leave an incomplete release or a visible conflict without remapping an accepted commit. Stage and promote only a bundle reached through a canonical receipt. Runtime configuration and website origins remain environment-specific without rebuilding images. [Container-level immutability](https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-container-level-worm-policies)

**Default-branch registration.** Propose one separately authorized, owner-reviewed maintenance PR to protected default branch `main`. It registers the staging dispatch and reconciliation workflows and applies the minimum workflow transition below. It does not require a milestone merge or a release tag. Keep S2 activation blocked until the PR lands, the approved workflow revision and environment rules are active, and a dispatch and rejection check proves the paths used on real refs. This prerequisite is part of task 3.1. Reject caller-supplied approval references, approvals for another action, tampered inputs and reruns. Require a fresh dispatch and approval after interruption when the previous attempt did not durably submit. A durable accepted operation is reconciled from its original ticket. Verify review visibility, approval history and proof/Entra claim binding in Phase B. ### 4. Durable staging session and shutdown

The offline candidate under Proposed [ADR-0013](../../../docs/architecture/adr/0013-staging-lifecycle-control-plane-and-identity.md) uses one small Azure Functions timer and HTTPS handler for S2, with durable Blob records outside the VMs. Flex Consumption with VNet integration is provisional. The controller reconciles against stored deadlines on every invocation, with a candidate cadence of one minute. Timer delivery and Azure operation latency can vary. Resume from persisted state after missed ticks and treat provider or controller outages as potentially delaying confirmed deallocation. The proposed bounds for S3 measurement are 30 minutes to reach startup readiness, up to five minutes to drain, and confirmation of both VMs within 15 minutes of session expiry, startup timeout or a cleanup request. Retry unresolved actions after that deadline with capped backoff. Rehearse and adjust thresholds from measured evidence and reserve the entire shutdown margin before the off window. During uncertainty deny new sessions, deployment approvals taking effect, workload activation and tester access. [Functions timer triggers](https://learn.microsoft.com/azure/azure-functions/functions-bindings-timer) · [Functions networking](https://learn.microsoft.com/en-us/azure/azure-functions/functions-networking-options)

Record a heartbeat only after a successful durable reconciliation. The controller and App gate reject stale state locally, using a candidate three-minute maximum heartbeat age and short-lived authorizations. A separate Azure Monitor scheduled alert and action group evaluate for a missing heartbeat even when the controller is down. Seed the alert query with the expected controller identity so zero heartbeat rows can trigger it. Start with a five-minute missing-heartbeat threshold and measure alert ingestion and notification delay. On missed cleanup or controller outage, an owner-authorized operator can use the separate deallocate-only identity even if GitHub or the controller is unavailable. It may read and deallocate only the named pair. Confirm both instance-view power states and record per-VM outcomes. On restart after stale state, reconcile any pending ARM operation and treat unexpected power states as recovery-required. Never reissue a start for an ambiguous generation. Require fresh verified admission before either VM can be started again. The monitor sends alerts. There is one shutdown controller per S2 environment. [Azure Monitor alert types and limitations](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-types)

1. **Off → Starting.** Persist the generation, owner approval, boot deadline and expected VM targets before submitting any power operation. Serialize through Blob conditional writes and record per-VM intents before ARM calls. The controller checks both Azure states and App-reported k3s/required service readiness. An empty environment permits the separately approved first deployment during the boot allowance. Tester access opens only when both nodes and required services are verified. Reject a second start against an existing or unresolved generation.
2. **Starting → Ready.** Apply the boot and recovery gate below before activating any release. Open tester access after the authorized release and both nodes reach readiness, then start the one-hour clock. Use UTC for persisted times and an explicit Asia/Ho_Chi_Minh daily off window. The candidate is 00:00–12:00 local time, with owner confirmation required before configuring it. Admit startup only if bounded boot, the full ready session and shutdown margin fit. Verify at least 12 hours deallocated per day from both VMs' observed states. An extension needs new owner approval against the same generation and cannot revive expired or draining state.
3. **Admit one change.** Use per-generation conditional transitions for deployment, rollback, migration and cleanup. Reserve a bounded operation window that fits the remaining boot/session time, with cancellation, reconciliation and shutdown margin. Recheck generation, request, deadline, approval and the contest freeze before a planned change. A freeze never prevents safety shutdown. Adopt/reconcile an accepted operation if its GitHub run exits, and mark unknown outcomes explicitly. A lost controller or App lease stops new mutations. The expiry controller accounts for an outstanding operation even while it owns the exclusive cleanup path.
4. **Ready or Starting → Draining.** The tester lease ends at expiry or earlier if state is stale. Close new official submissions, rejudges, Run Code and other writes, then suspend Worker consumption and verify group membership and offsets. Allow bounded completion or safe interruption of in-flight work. Any drain authorization is limited to the previously active processes needed for shutdown until the drain deadline. Stop Submission after the result consumer and outbox relay settle or have a recorded durable pending state. Compare accepted attempt state, outbox, Kafka lag/offsets, DLT and unapplied results. Retain official work for redelivery or operator reconciliation and verify existing attempt guards on restart. The known outbox and DLT limitations remain tracked by their existing work.
5. **Draining → Off or Recovery required.** When drain completes or its hard deadline expires, automatically deallocate both VMs and retain disks. Poll Azure instance view for `PowerState/deallocated` on each VM. Treat a late start, timeout or unknown response as outstanding work. Retain long-running operation identities when available, reconcile them before declaring Off, and repeat deallocation of either live VM. At the cleanup deadline record unresolved work and alert. Resume from durable state after controller restart. An Actions result, stale status or only one deallocated VM cannot establish cleanup success.

**S3 experiment cleanup.** Before applying a plan that can create or start either S3 VM, record an owner-approved experiment deadline and the exact pair and disposable inventory. Run the same timer code with deallocate-only power permissions, in a temporary operations scope outside the experiment workload resource group, and verify the timer and independent alert are armed. The same instance can serve the protected operator's rehearsal-only ticket and permit path for testing App pull and recovery. That path cannot grant S2 access, move the experiment deadline or start VMs. Any S3 power-on needed for the experiment remains with the separately authorized infrastructure operator and must fit the recorded deadline. The timer retains its deadline after a test runner or Terraform session exits, deallocates only the two targets by the same power-state checks, and raises an inventory follow-up. The operator compares approved plan, Terraform state and Azure inventory, removes only reviewed leftovers, and retires the timer and monitoring after confirmation. Keep the emergency role and unfinished inventory visible until then.

An S3 hard-stop resume ticket binds the protected caller, experiment and one interrupted operation. It requires confirmed deallocation of both nodes, has a bounded external power-on window and keeps the earlier of the original session and experiment deadlines. It requires two fresh kernel boots and preserves the old operation and Job evidence until the separately authorized workload recovery. A sealed partial migration leaves workload admission closed and permits a separate forward deployment of the same reviewed release on the verified epochs.

### 5. Managed migration, activation and rollback

**Boot and recovery gate.** Persist the last verified activation and any in-flight mutation in the controller's Blob record, including the authorized session generation, operation, exact release and config digests, migration artifact and all three verified owner histories, and clean drain or recovery outcome. Mark a mutation in progress before granting any authorization that can change state. Update the last verified activation only after rollout readiness and smoke succeed. An in-flight or unknown record is retained across hard shutdown and starts in recovery-required state.

1. On restart of either VM or its cluster services, start the control plane, verified backing stores and minimum management/recovery processes. Invalidate prior authorization using a new node/cluster startup epoch, and start with no cached grants. Keep testers, application processes, the Worker/executor and migration Jobs closed while the controller and App verify the actual boot state and durable record.
2. Use a platform-owned launch guard as the supervisor for every application, judge and migrator container process, including every kubelet restart of an existing container. The trusted workload templates fix the guard, original command and read-only permit path. The host services install short-lived, authenticated permits scoped to the environment, current startup epochs of both nodes, session and operation, workload, approved image/config digest and expiry. Give Judge only access to its own permits through the private node path. The guard withholds the application or migration child until the permit matches, and terminates it on expiry or loss of authorization. A migration permit is single-use for the specific Job attempt with current preflight and writer lock. A stale desired-state object, old Job, cached grant or permissive owner version check grants no execution. Treat an unconfirmed stop as a recovery condition. The executor guard relies on the trusted Judge host and daemon. Admission, NetworkPolicies and the in-container guard provide no independent protection against a compromised daemon.
3. For a clean restart, verify the last approved release, drain and exact all-owner history, then issue fresh runtime permits for that release without rerunning migrations. For a partial migration or candidate rollout, keep DDL, outbox relay, result consumer and judging closed. Reconcile the actual PostgreSQL histories, stale credentials and sessions, running digests, worker state and retained work. Resume only after authorized recovery verifies a known compatible state. A separately authorized forward fix may receive a fresh migration permit after preflight and fencing. Issue runtime permits only after all three histories and termination checks pass. Check readiness and smoke before granting the tester lease. On a fresh environment the first deploy must be separately approved before any application permits issue.

**Managed rollout procedure**

1. Verify the protected session and exact release. Prepare PostgreSQL and three independent managed databases and roles before migration. Use separate migrator and runtime credentials and permissions. Grant each runtime role DML and version-read privileges in its own database. Verify fresh databases or known applied prefixes, the proposed schema and release history, target identity, backup/recovery point, migration hashes and rollback compatibility for all three before any writes. Refuse unexpected history, nonempty legacy schemas without trusted history, and drift. Reviewed seeds remain explicit.
2. Publish the current SQL sets with official Goose v3.30.0 and a managed entry point so Compose can keep its local wrapper. Use one protected environment operation and per-database PostgreSQL session advisory locks from read-only preflight through post-check. The CLI opens separate connections, so persist a database operation marker before granting run-specific migration access. Clear the marker only after the CLI exits, its DB sessions are confirmed closed and history/schema checks succeed. All entry points refuse an unresolved marker even if the advisory lock has been released. On lock loss, cancel the job, fence the stale credential and verify its sessions are gone before separately authorizing reconciliation. Use deadlines for acquisition, DDL locks and statements. Never infer safety from a Kubernetes Job terminal state alone. A partially applied sequence records per-owner results and leaves activation closed until reviewed reconciliation. [Goose v3.30.0 CLI](https://github.com/pressly/goose/blob/v3.30.0/cmd/goose/main.go)
3. Quiesce judging and affected application traffic for protected rollout, following the existing Worker suspension and group-empty checks. For Submission, scale to zero and verify the prior Pod UID's containers and relay actually stopped on the healthy App node before starting the replacement. A terminating Pod, lost node, forced API deletion or stale status cannot authorize replacement. Require the same checks on rollback and reopen the edge only after all workloads report readiness, the private Problem contract probe passes, and the exact candidate passes the smoke suite.
4. Roll back only to a previously verified DDL-free release compatible with the live schema, restoring App before its matching Judge. Keep schema versions and current secrets. Current `pkg/schema/startup.go` requires exact version equality, so rehearse the ≤15-minute rollback between two releases with the same schema and explicitly test refusal of a previous release after a version advance. A release that advances the schema needs a separately verified rollback artifact whose startup checks accept the resulting versions or a reviewed recovery path before approval. If an accepted rollback requirement cannot be met, fail closed and bring it to review. Schema repair uses a reviewed forward fix or restore, with no automatic down migration.

## Risks / Trade-offs

| Risk | Mitigation |
| --- | --- |
| A single App node and App disk carry control plane and data dependencies. | Keep startup fail-closed on the mount. Rehearse reattachment and preserve metadata and pre-migration recovery points. |
| Private VXLAN does not encrypt cluster traffic and privileged execution resides on Judge. | Limit tenancy and permitted paths, check staging transport and credential isolation in S3 and S2, and block exposure if a boundary fails. |
| Tenant or offer constraints may invalidate state access, Flex Consumption, OIDC, region, VM SKUs, public IPs, Key Vault or budget delivery. | Verify permissions, availability, estimated cost and binding in read-only preflight. Escalate an ineligible design to the Orchestrator and use ADR review for any change to the architecture. |
| A partial rollout can leave a schema ahead of the last image or a valid official job pending. | Record actual per-owner versions and retained attempt state. Prevent automatic application activation, destructive rollback and stale takeover. |
| Azure control-plane delays and actual charges can fall outside estimates. | Keep operation deadlines, independently retry including uncertain VM operations, verify power states, and wait for cost data before closing Phase B. |
