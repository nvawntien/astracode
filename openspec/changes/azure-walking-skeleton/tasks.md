## 2. Phase B — Authorized Azure validation and acceptance

Phase B requires explicit project-owner authorization for cloud operations. S1 production activation and deployment stay outside this change. Canonical S2 release evidence must come from the protected `develop` publication path.

- [ ] 2.1 Activate and map S1–S5 with the project owner. Record sanitized preflight for credits, expiry, tenant access, IAM, resource providers, regional and family quotas, SKU and offer restrictions, GHCR, OIDC, GitHub approval features, candidate egress and controller plans, and estimated costs. Require verified target access before any provisioning (ED-01, ED-04, ED-10).
- [ ] 2.2 Bootstrap S4 and move its bootstrap state to Azure Blob. Verify least-privilege backend access, native lock contention, independent environment state access and isolation across tenants where applicable, protected state and backup scopes, and named recovery access (ED-01).
- [ ] 2.3 Provision a disposable S3 pair using the reviewed plan and time environment recreation from the first environment provisioning action to verified application readiness. Record prerequisites and the ≤2-hour result, state isolation, node placement, mount fail-closed behavior and disk reattachment. Verify actual node/cluster versions, default outbound disabled, private dependency reachability, denial of unauthorized access, and go-judge resource limits and isolation with synthetic workloads. Rehearse a failed managed migration against disposable data and confirm activation is blocked (ED-01, ED-02, ED-06).
- [ ] 2.4 Measure S3 idle and representative-load CPU, RAM, k3s overhead, disk/cache use and growth, B-series burst behavior, networking and initial billed costs. Validate effective limits, sizes and budget notification delivery, then destroy only the reviewed temporary S3 resources. Verify the residual resource and cost inventory against the disposable plan (ED-10).
- [ ] 2.5 Provision S2 using the validated sizing and reviewed plan. Arm the controller before VM creation, verify approved provisioning, target-specific credentials, registry digest pulls, private API and SSH, tester HTTPS membership and agent-token rotation/rejoin. Record the staging state and data retention boundaries (ED-01, ED-02, ED-04).
- [ ] 2.6 Exercise real protected publication, approvals and deployment on S2. Compare exact CI and runtime digests, source/config revision and migration evidence. Verify separate first-start and deploy approvals, rejection of unauthorized and replayed operations, first-start readiness and successful smoke for sign-in, catalogue, official submission to Verdict, Rejudge and SSE, and synchronous Run Code with synthetic data. Exercise future promotion eligibility without provisioning or deploying production (ED-02–ED-06, ED-09).
- [ ] 2.7 Rehearse compatible S2 rollback within 15 minutes and staging shutdown with active work, failure or cancellation, and partial cleanup. Record prior Submission termination, applied versions, timed readiness/expiry and extension, refusal of unsafe or concurrent operations, durable work reconciliation, alerts and retry outcomes, both VM power states, the 12-hour daily off-time observation and persistence on restart (ED-05–ED-08).
- [ ] 2.8 Publish sanitized acceptance evidence linking each spec scenario to an automated result or recorded check. Include S3 recreation timings and measured sizing, S2 release/approval/rollback and lifecycle records, actual accrued costs and cost forecast per relevant subscription, 50/80/100% budget configuration and notification checks, and remaining limitations. Keep any criterion lacking real evidence open (ED-01–ED-10).
