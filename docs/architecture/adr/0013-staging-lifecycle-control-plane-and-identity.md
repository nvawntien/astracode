## Context

ADR-0004 assigns startup of both staging VMs to GitHub Actions and Azure CLI. The offline candidate hands approved requests to an independent Azure Functions controller whose identity starts the S2 pair. Its HTTPS API uses a delegated Entra member caller and separately scoped machine callers. The controller also owns deadline and power reconciliation after the workflow exits. That candidate remains offline pending this decision.

Reported preflight shows subscription Owner access for the respective S2, S3 and S4 operators, provider registration in the target subscriptions and listing support for the candidate storage and Functions region. The tenant A member accounts report no directory roles and tenant A prohibits member app creation. Directory administrator assistance, a delegated app-registration route and a suitable existing API are all unconfirmed. Tenant B allowing members to register apps does not establish a tenant A enterprise application, consent or app-role assignments. The remaining project window is 14–21 days. [Azure preflight observations](../../evidence/m0-13-phase-a.md#azure-preflight-observations)

## Alternatives

Estimates are engineering days for a reviewable implementation and offline verification. They exclude external waits, Orchestrator decisions and the authorized live S3/S2 acceptance exercises.

| Alternative | Security, operations and delivery |
| --- | --- |
| **A. Controller-owned power and custom Entra API** | Keeps the existing authority model, independent cleanup and short, synchronous authorization checks. Requires a confirmed tenant A directory actor or delegation to register the API and member client, establish service principals, configure a delegated scope and consent, and assign separate application roles as required. Azure RBAC still governs app hosting, Storage, VM power, and Azure resource federation. The API team operates audiences, token validation, directory grants and public HTTPS endpoint protection. Most code is reusable. Estimate 1–3 days after verified directory access. The external wait is unbounded and can consume the delivery window. |
| **B. ADR-0004 direct GitHub workflow startup and independent cleanup** | Azure resource federation can give a protected job pair-scoped VM read and start actions without registering a custom API for the ARM call. A compromised job that obtains this role can call ARM directly and bypass controller admission. The controller must arm cleanup and record the deadline before start, then reconcile partial starts or missing acknowledgements. The monitor and deallocate-only emergency path remain separate. Member requests and App authorization still require a supported path. Retaining the current HTTPS API for them inherits A's directory blocker. Estimate 3–5 days for startup handoff and verification, plus any redesign and validation of those remaining paths. Similar baseline Azure hosting cost, with an extra serialized handoff to operate and audit. |
| **C. GitHub approval, federated managed identities and scoped Blob transport** | GitHub authenticates requesters and gates dispatch. Protected jobs write approved envelopes with federated user-assigned managed identities (UAMIs). The controller independently verifies approval, commits authority and performs S2 power operations. A separate App managed identity reads grants and reports observations. This removes the custom API's app registration and app-role lifecycle. It requires proven create-only Storage access, a protected runner network path, and measured admission, freshness and revocation. Blob transactions, polling, Functions invocations and private connectivity add cost. Estimate 4–7 days, including a 1–2 day feasibility spike, if available runner and Function paths meet the gates below. A new runner tier, continuous fast reconciler, or unconfirmed product eligibility can invalidate that estimate. |

## Proposed decision

Prefer **C** if the target offer and repository can meet the permission, network, approval and timing gates below with one independent Function app and a small set of scoped Blob containers. This retains controller-owned power without depending on directory assistance or giving CI the ability to start VMs directly. Treat the authenticated storage path and bounded authorization latency as go/no-go checks before wider implementation. If either fails, keep activation closed and return to the Orchestrator. A is viable only with confirmed directory grants. B alone leaves an approval bypass and an unresolved App and member authentication path. Use native approval on the public repository. If it is unavailable, an equivalent protected approval mechanism needs separate review.

### Request, approval and authority

| Actor | Authority under C |
| --- | --- |
| Authorized member | Use a protected GitHub request channel. Derive the requester from the authenticated GitHub event and an explicit member allowlist of immutable account IDs. Freeze the typed request and verify its source record. A copied body, freely supplied requester ID or edited issue/comment cannot establish authorization. Requesting confers no approval, Storage write or Azure power rights. |
| Project owner and designated maintainers | Owner approves lifecycle startup and extensions. Either designated deployment maintainer can approve deployment or rollback. Promotion eligibility remains independently gated. Use distinct GitHub environments, protected `main`, required reviewers, self-review prevention and disabled administrator bypass. An eligible requester can have a separate authorized member dispatch the frozen request. Check role, source, dispatcher and reviewer independently. |
| Protected GitHub job | Bind the exact typed payload and request ID to the target, action, release or Terraform plan where applicable, current session or generation, and expiry. Freeze the digest before native approval and give the reviewer access to that exact request through the protected review path. After approval, bind it to the immutable repository, workflow revision, environment, run and attempt using the existing digest-audience GitHub proof pattern. Exchange a separate Azure-audience GitHub OIDC token for a role-specific UAMI. The job can create inputs only in its assigned command container and read scoped sanitized results. It has no approval, VM power, state, backup or runtime secret authority. |
| Independent controller verifier | Verify the signed, short-lived GitHub proof against the frozen request and protected repository, ref and workflow revision. Check live run and review history directly with GitHub for the correct environment and permitted reviewer, including attempt and requester/dispatcher separation. Record the one-time admission and deadline before any effect. A successful Storage write provides transport access only. Preserve first-attempt-only admission unless the review API can prove an exact later attempt. |
| Azure VM power principals | The S2 Function identity owns routine read, start and deallocate on the exact pair. Only the separate plan-bound infrastructure operator may create or replace VMs with a current approved window and cleanup armed. The S3 controller can observe and deallocate only. Its separate authorized operator may perform a bounded rehearsal or recovery start under a single-use grant. |
| App poller | Use a dedicated App managed identity to read scoped current grants and create observations for its environment. No writes to the command inbox, trusted grants or ledger. The controller checks the epoch, operation and ordering of observations before any state change. Keep the private rollout path and the host/IMDS boundary. |
| Independent cleanup and emergency operator | The Function timer reconciles persisted deadlines and Azure power state independently of GitHub and App. Separate monitoring alerts on lost health or uncertain cleanup. The emergency identity can read state and deallocate only the target pair, without GitHub, App or the controller. Require observation of both VMs' deallocated states before reporting shutdown complete. |
| Release publisher | Retains separate S4 receipt publication scope. No command submission, VM power or staging state writes. Staging identities gain no authority to replace canonical receipts or access Terraform state or backups. |

For the public repository, GitHub documents native reviewer protections and read access to public workflow review history. The verifier still has to demonstrate exact run/environment binding, availability within proof lifetime and fail-closed handling of API outages or rate limits. Keep the approval workflow alive for a bounded admission acknowledgement while its proof is valid. The mailbox must never contain Azure access tokens, shared keys or general-purpose credentials. Protect and expire the brief command proof, and exclude it from logs and status. Recovery uses the durable, verified admission record within its original bounds. [GitHub environment protection](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) · [GitHub OIDC claims](https://docs.github.com/en/actions/reference/security/oidc) · [Workflow review history API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run)

### Feasibility with existing Azure access

- **Resource grants.** UAMI creation and its federated credential use `Microsoft.ManagedIdentity/userAssignedIdentities/write` and `Microsoft.ManagedIdentity/userAssignedIdentities/federatedIdentityCredentials/write`. The bootstrap operator needs these actions and `Microsoft.Authorization/roleAssignments/write` at the intended scopes, plus `Microsoft.Authorization/roleDefinitions/write` at the assignable scope if defining custom roles. Reported subscription Owner access makes this plausible subject to policy and deny assignments. UAMI federation requires no custom API app registration, delegated consent, or app-role assignment. Validate the actual issuer, Azure audience and exact subject per environment with immutable repository identity. An environment-only subject does not bind the workflow. Verify the protected workflow constraint at federation if supported, and always bind the exact workflow revision at admission. Prove rejection for forks, wrong refs, workflows and environments. If subject customization is needed, verify it preserves the separate release publisher's federation. Keep federation separate from the controller's digest-bound approval verification. [Managed Identity Azure roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/identity) · [GitHub federation to a UAMI](https://learn.microsoft.com/en-us/azure/developer/github/connect-from-azure-identity) · [Azure custom roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles)
- **Data and power grants.** Separate the environment and role command scopes, App observations, authoritative ledger and read-only status. Use small block blobs with only `Microsoft.Storage/storageAccounts/blobServices/containers/blobs/add/action` for workflow inputs and App observations at their respective container scopes, and `…/blobs/read` only at the required result/grant scopes. Use `If-None-Match: *` and unique IDs. Prove authorization denies overwrite, delete and cross-scope access independent of client-supplied headers. Grant ledger writes only to the controller and keep host-storage rights out of workflow and App principals. Scope controller power to VM read and instance-view read plus `Microsoft.Compute/virtualMachines/start/action` and `…/deallocate/action` as allowed for each environment. Emergency and S3 controller roles omit start. Keep the separately scoped Terraform and S4 receipt roles. Do not fall back to an unrestricted Blob writer, account keys, shared credentials or anonymous access. [Put Blob permissions](https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob#permissions) · [Blob optimistic concurrency](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage)
- **Network and offer.** The candidate controller storage has a private endpoint and public access disabled. Verify private DNS, TLS and reachability from Function and App, as well as a protected runner with an approved route to the command/status containers and S4 receipt scope. The current standard GitHub-hosted runner has no automatic VNet route. Check an available isolated, protected runner on the private path first. GitHub's managed VNet integration requires an eligible organization and larger runner, neither confirmed. A mailbox-only network-allowlisted endpoint would require a proven fixed egress and policy approval, with no broad runner IP ranges and no exposure of private state or backups. Keep the runner off App and Judge. Reported regional listings do not establish FC1 offer eligibility, package delivery, timer behavior, capacity, runner access or costs. Prove these within the current quotas and billing budget. [GitHub-hosted private networking](https://docs.github.com/en/organizations/managing-organization-settings/about-azure-private-networking-for-github-hosted-runners-in-your-organization) · [Functions networking](https://learn.microsoft.com/en-us/azure/azure-functions/functions-networking-options)
- **Concurrency and recovery.** The trusted ledger serializes admission, replay consumption, deadlines, observation generations and power intents with ETag compare-and-swap (`If-Match`). On conflict reread and revalidate against current state. Record the intent before an ARM call and reconcile the observed effect before retry. Exact repeats may receive the prior result but do not renew a grant. Wrong generations, modified payloads, expired proofs and replayed attempts must be rejected. A workflow exit, Blob failure, missing acknowledgement or partial stop must leave durable, bounded authority with no new workload admission during uncertainty. Preserve independent alerts and emergency access if reconciliation itself fails.
- **Expiry and timing.** Keep the independent monitored timer for power and cleanup. Its minute cadence cannot replace the current five-second tester grants, 15-second App freshness and short process permits. The App poller reads authoritative grants and checks cancellation, source freshness, session/operation expiry, node epochs and expected digests. It can renew only within the current confirmed grant. Missing or stale status must close tester access and prevent activation, including when Blob or Functions is unavailable. Measure the complete command, observation, issuance and revocation loop. If needed, assess bounded faster reconciliation in the same Function app before adding any new service. Test cold starts, missed ticks, conflicts, loss of runner and loss of connectivity, and cost at the measured cadence. No extension of stale authorization to compensate for transport delay. A Flex Consumption Blob trigger, if considered, requires Event Grid and would need its own network, timing and cost proof. [Timer behavior](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-timer) · [Flex Consumption constraints](https://learn.microsoft.com/en-us/azure/azure-functions/flex-consumption-plan)

## Effect on ADR-0004

If accepted, C supersedes only the allocation of direct VM start to GitHub Actions in item 1 of [Staging lifecycle](0004-azure-topology-and-subscription-layout.md#staging-lifecycle) and the direct-power implication of its immediately following paragraph assigning implementation to GitHub Actions and Azure CLI. GitHub still owns approval and dispatch. This extends the last bullet of [Delivery and access control](0004-azure-topology-and-subscription-layout.md#delivery-and-access-control), on scoped OIDC and private delivery, by separating the workflow, verifier, App and Azure power identities. The topology, infrastructure/application separation, approval roles, readiness measurement, session duration and off-time floor, independent cleanup and data retention remain in force.

## Consequences and validation

Reuse protected workflow dispatch and request freezing, GitHub proof and review verification, the controller timer and ETag ledger, exact VM intents, monitoring and emergency tooling, digest-bound release/receipt validation, App pull and local permit enforcement. If implemented, C replaces the custom Entra member and machine API, role/consent setup and public Function handler with GitHub request identity, UAMI-based job and App adapters, scoped mailbox state and asynchronous acknowledgements. Preserve the migration, rollback and promotion fences. No runner on the data host, guest exec for routine rollout or permanent runner service is assumed. Estimate recurrence, Blob transactions, retention, private connectivity and any additional GitHub runner cost before provisioning. A short, separately authorized live timing trial would establish whether one Function is enough. Implementation awaits approval.

The two lifecycle findings remain open independently of the identity decision.

| Finding | Effect of the alternatives |
| --- | --- |
| S2 initial provisioning can fail daily off-time admission before the VMs exist | A retains the current coupling between plan-window admission and staging off-time accounting. B moves routine VM startup but still needs separate plan-bound Terraform admission. C retains the same ledger and rules, and can simplify the entry path by separating reviewed infrastructure intent from routine session start. It still needs an explicit, reviewed accounting rule for a fresh environment. Never count a missing VM as observed deallocated. |
| Failed delete-before-create replacement can leave no authorized recovery | A retains the gate that rejects missing targets for replacement. B changes only the routine start principal. GitHub start cannot recreate a missing VM. C can reuse the durable plan/intent record to authorize a separately approved, single-use recovery of the exact missing target. It still needs a recovery transition that confirms the retained disk/network identity, plan, generation and deadline, with cleanup armed and workload activation fenced. |

Any implementation must verify [ED-01–ED-10](../../../openspec/changes/azure-walking-skeleton/specs/environment-delivery/spec.md) and the [applicable quality targets](../../product/nfr.md). In particular ED-04 requires one exact approval per attempt, ED-05 and NFR-F03 require the readiness-based session and daily off-time floor, and ED-06–ED-08 require fail-closed activation and independent bounded recovery. ED-01/NFR-D04 require the complete empty-target recreation within two hours. ED-03 and ED-09 keep the canonical release and promotion proof separate. ED-02 and ADR-0012 still require live S3 isolation for the actual Judge workload.

Microsoft and GitHub documentation establish the general capabilities above. The project's preflight records reported access and listings only. Live validation must prove the request-to-approval path, federation and least-privilege denials, exact-run and replay resistance, mutable-write denials, conflicting admissions, network paths, timing and fail-closed behavior, partial and stale recovery, observed power states and budget impact. Verify the independent S4 receipt boundary and exercise the separate emergency role. Record those results through ED-10 and the existing [M0-13 acceptance tasks](../../../openspec/changes/azure-walking-skeleton/tasks.md). Task 2.1 remains open.
